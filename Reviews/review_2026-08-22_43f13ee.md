## 0. Disposition of review #10 — all four items closed, three with measurement

**§1 the 65-minute re-run — done, and it closes the reconciliation finding.** All 34 prior backward
jumps and the 24.10 s overflow are gone: zero discontinuities, zero segments beyond media duration,

**§2.1 the O(n²) duplicate scan — fixed better than proposed.** Beyond reordering the predicate and

concurrent overlaps rather than O(n²), and the unchanged RTF confirms it is no longer a cost.

**§2.2 nil `seekTime` — fixed.** Now falls back to the previous window's end and emits a typed
`window_seek_repaired` diagnostic distinguishing missing from invalid, rather than silently
defaulting to 0. The 65-minute run reported none, which is itself worth knowing.

**§2.3 exact-match duplicates — answered empirically rather than argued.** `overlappingSurvivorCount`
was added specifically to test whether partial duplicates were slipping through, and it returned
zero on 1,594 segments. That is the right way to close a speculative concern.

**§3 the blocklist — resolved with the better of the three options I offered.** Visible quarantine
retains the source line annotated `[suspected-hallucination]`, withholds translation, and keeps it
out of context (`TranslationPipeline.swift:143-156`). It avoids deleting a legitimate closing line
without needing a new energy signal, and it leaves the judgment with the reader. Simpler and more
robust than the corroborating-condition approach I recommended.

**§4 the latency model — recorded**, with the segmenter tradeoff and the batching lever both noted
in the doc.

Also worth crediting: adopting `ChunkingStrategy.none` with the adapter's own `VADAudioChunker` is
the strategic convergence suggested earlier — the file path now uses the chunking machinery live
capture will need, rather than two mechanisms.

One speculation of mine did not pan out: I suggested fixing the overlap might recover some RTF,

self-chunking replaced the SDK's overlapping windows entirely, so the re-decode cost was never

## 1. `bfish transcribe` crashes on MP3 — the primary format for the primary use case

`docs/whisperkit-long-form-2026-08-21.md:48`

> The two-speaker fixture was normalized to a temporary 16 kHz mono PCM file because seeking the
> compressed MP3 directly through `AVAudioFile` raised an Objective-C Core Audio exception.

This is recorded as "an adapter issue to resolve separately," but the severity deserves raising,
because of *how* it fails.

An Objective-C `NSException` is **not catchable from Swift**. There is no `do`/`catch` that
intercepts it. So this is not an error the user sees — it is a process abort with no message, no
diagnostic, and no JSONL record. The streaming path at `WhisperKitRecognizer.swift:246` and
`:277-284` seeks repeatedly via `AudioProcessor.loadAudio(fromFile:startTime:endTime:)`, so any
compressed input that cannot be seeked reliably will trip it.

Podcasts are MP3. The stated use case is podcasts. So the most likely real invocation of the tool
crashes, and the working procedure — convert to 16 kHz mono PCM first — is documented only inside a
probe doc, not in the README or the command's help text.

There is also no guard: nothing inspects the input format before entering the seek loop.

Two fixes, and I would do both:

1. **Detect and decode up front.** If the input is not seekable linear PCM, decode it once to a
   temporary PCM file (or an in-memory buffer for short inputs) and proceed from that. This is what
   was done by hand for the 65-minute run, so the procedure is already known to work; automating it
   makes the common case just work.
2. **Fail clearly if that is deferred.** At minimum, check the file's format before the first seek
   and throw a typed `WhisperKitRecognizerError` naming the format and the conversion command. A
   clear Swift error is vastly better than an uncatchable abort, and it is a few lines.

Until one of these lands, the README's `bfish transcribe ./sample.wav` example is quietly
load-bearing: it works because it says `.wav`.

## 2. The 15.9-second undershoot is probably benign, but worth one check

The reconciled 65-minute run ends at 3,890.04 s against 3,905.92 s of media — 15.88 s short. Before
the fix it *overflowed* by 24.10 s, so the sign has flipped.

Forty-two segments were discarded as wholly outside their authoritative windows. Those were not
matched against a duplicate; they were dropped for being out of bounds. The theory that makes this
safe is sound: if window *N* emits content past its own end, window *N+1* covers that region and
transcribes it properly, so nothing is lost. The zero `overlappingSurvivorCount` is consistent with
that — if both copies had survived, they would register as overlaps.

But `overlappingSurvivorCount` measures whether *retained* segments overlap. It does not measure
whether *removed* content was recovered. Those are different questions, and only the first has been
answered.

The cheap discriminator, computable from data already in the JSONL: **is the missing 15.88 s one
contiguous tail, or distributed across the file?** Sum the inter-segment gaps and compare against
the final gap. A single tail gap means outro music or trailing silence — entirely expected for a
podcast, and the 8:39 fixture's 3.9 s shortfall supports that reading. Gaps distributed near the 42
removal points would mean real content was dropped.

I would rate this likely benign (~75%), but it is the one place where the fix could be silently
lossy, and the check is a few minutes of analysis on existing output.

## 3. The before/after comparison confounds three variables

The doc places 1,623 pre-fix segments next to 1,594 post-fix segments. Read casually that suggests
29 duplicates were removed. It does not mean that, and the difference should not be interpreted:

| | pre-fix run | post-fix run |
|---|---|---|
| chunking | WhisperKit `.vad` | adapter `VADAudioChunker`, `ChunkingStrategy.none` |
| audio path | MP3 direct | normalized 16 kHz mono PCM |
| reconciliation | none | v14 |

Three changes at once, and the first alone produces entirely different segment boundaries — 177
windows now, versus an unreported count before. Segment counts are simply not comparable across
these runs.

This does not weaken the result: zero discontinuities, zero overflow, and zero overlapping survivors
are absolute properties, not deltas, and they stand on their own. Worth a one-line note in the doc
so a future reader does not derive a duplicate-removal rate from the segment counts.

## 4. Memory metrics still do not answer the contention question

`physicalFootprintBytes` was added as recommended, and the 65-minute run reports 190.8 MiB RSS
against 90.8 MiB physical footprint. The footprint being *lower* than RSS is consistent with the
earlier reading that mapped and shared pages inflate RSS.

Both numbers remain implausibly small for a process with a 626 MB model loaded, which reinforces
that neither captures the model's weights — whether mapped, ANE-resident, or otherwise outside
per-task accounting.

That is fine for tracking the adapter's own allocation behaviour, which is what these metrics now do
well. It is not fine as an input to `README.md:441`'s question of whether `large-v3` and a 7–8 B
translation model can coexist. Planning concurrency from 90.8 MiB would be badly optimistic.

When the bake-off runs, the measurement that matters is **system-level**: total and available
unified memory, memory pressure state, and swap activity while both models are resident — not
per-process accounting from either metric.

## 5. Smaller notes

**First-segment latency is now measured: 1,973 ms** on a 65-minute file. That is a good
user-experience number and it makes the streaming claim quantitative rather than qualitative, which
was the review #10 §5 request. Worth carrying into the live budget discussion — it sits inside the
3–4 second subtitle target with room for translation.

**The quarantine disposition needs a formatter contract.** `qualityDisposition` reaches
`TranscriptTurn` and both formatters were touched, so the `[suspected-hallucination]` annotation
renders. Worth confirming the annotation is also distinguishable in the JSONL for a downstream
consumer — a benchmark harness scoring CER should exclude quarantined lines, and it needs a
machine-readable way to identify them beyond parsing the terminal string.

**Real music and speech-over-music remain untested.** Unchanged from review #10, and correctly
flagged in the probe doc. The current safeguards are validated against digital silence and
synthesized tones only.

4. Then the translation bake-off. Recognition is now measured, reconciled, streaming, and
   memory-stable; §4's latency data and the 1,973 ms first-segment number give the bake-off a real
   budget to design against.

The recognition workstream looks essentially complete for file mode. The remaining items here are a
robustness guard and a verification pass, not new capability.
