## 1. New defects introduced in this commit

### 1.1 The packaged app crashes when `.build/` is absent — verified

`Sources/BFishCore/BFishCore.swift:5-10`, `Package.swift:17`, `Scripts/package-local.sh:15-18`

`BFishCore.version` reads `Bundle.module`. `package-local.sh` copies the binary and the Info.plist
into the `.app`, but **never copies the SwiftPM resource bundle** `bfish_BFishCore.bundle`.

The packaged app appears to work only because SwiftPM bakes the absolute build path into the
generated accessor and `.build/` still exists on the build machine. Remove it and the app dies:

```
$ mv .build/arm64-apple-macosx/release/bfish_BFishCore.bundle{,.hidden}
$ .build/artifacts/bfish.app/Contents/MacOS/bfish version
BFishCore/resource_bundle_accessor.swift:12: Fatal error: could not load resource bundle:
  from /Users/…/.build/artifacts/bfish.app/bfish_BFishCore.bundle
  or /Users/…/.build/arm64-apple-macosx/release/bfish_BFishCore.bundle
EXIT=133
```

Failure scenario: `swift package clean`, or copying the `.app` to another Mac, or any move off the
build path → hard trap (SIGTRAP) on `bfish version`, and on every code path that touches
`BFishCore.version`.

Note also that the defensive `else { return "unknown" }` in `BFishCore.swift:8` is **unreachable**.
SwiftPM's generated accessor calls `fatalError` before the `guard` ever evaluates, so the graceful
fallback provides no protection.

Fix: either copy the resource bundle into `Contents/Resources/` in the packaging script, or drop
the resource entirely and inject the version at build time. Given that VERSION is a single short
string, a generated Swift constant or a plist read is simpler than a resource bundle and removes
the failure mode. The regression traded a cosmetic duplication problem for a crash.

### 1.2 The transcript stream silently drops output under backpressure

`Sources/BFishCore/Pipeline/TranslationPipeline.swift:45`

```swift
return AsyncThrowingStream(bufferingPolicy: .bufferingNewest(64)) { continuation in
```

`.bufferingNewest(64)` was the right fix for the **audio** channel, where dropping stale frames is
acceptable and must be reported. It has been applied to the **transcript output** channel, where a
drop is silent data loss: `bufferingNewest` discards the *oldest* buffered element once full, and
the `yield` return value (`.enqueued` / `.dropped` / `.terminated`) is discarded at every call site.

So a consumer that lags — writing to a slow terminal, piping into another process, rendering in a
future SwiftUI view — loses finished translated turns with no error, no diagnostic, and no gap in
the numbering to notice. `DiagnosticEventKind` has `audioChunksDropped` but no transcript
equivalent, so there is not even a way to report it.

The exposure is currently bounded because the producer awaits `translator.translate` per segment and
cannot run far ahead. It stops being bounded the moment translation is fast (Apple Translation, or
the English-bypass path at `TranslationPipeline.swift:52-57`, which yields with no await at all) and
the consumer is slow.

Recommendation: transcripts are the product's output and should never be dropped. Use unbounded
buffering for the transcript channel, or add real backpressure. Reserve `bufferingNewest` for audio.
If a bound is kept, check the `yield` result and emit a `transcriptDropped` diagnostic.

### 1.3 `boundedContext` can silently omit the most recent turn

`Sources/BFishCore/Pipeline/TranslationPipeline.swift:109-126`

```swift
for turn in turns.suffix(turnLimit).reversed() {
    let cost = turn.sourceText.count
    if !result.isEmpty, characters + cost > characterLimit { break }
    guard cost <= characterLimit else { continue }
    result.append(turn)
    characters += cost
}
```

The `break` is guarded on `!result.isEmpty`, and the oversize check is `continue`, not `break`. So
when the **most recent** turn alone exceeds `characterLimit`, it is skipped, `result` is still empty,
and the loop keeps walking backwards admitting *older* turns.

Walk-through with `turnLimit: 4`, `characterLimit: 100`, turns newest-first `C(500), B(10), A(10)`:

| turn | `result.isEmpty` | action |
|---|---|---|
| C (500) | yes → break check skipped | `guard 500 <= 100` fails → **continue** |
| B (10)  | yes → break check skipped | append B |
| A (10)  | no, 20 ≤ 100 | append A |

Result: context `[A, B]`. Turn C — the utterance immediately preceding the one being translated — is
gone, and the model receives A and B as though they were adjacent to the current segment. This is
exactly the silent context discontinuity review #1 flagged in §4.2, reintroduced through the new
character-budget code.

Realistic trigger: one long monologue turn immediately before the current utterance. Common in
podcasts and interviews — the primary offline use case.

Secondary issue in the same function: `cost` counts `turn.sourceText.count` only and ignores
`englishText`. If the prompt includes prior English (likely, since context exists to disambiguate and
the model emits English), actual prompt size is roughly **twice** the budget. Since the entire point
of the character limit was making p95 latency predictable, a 2x systematic undercount defeats it.

This function is untested. A single test over the table above would have caught it.

### 1.4 `WhisperLanguage` as a closed 9-case enum contradicts a stated project goal

`Sources/BFishCore/Domain/LanguageTag.swift:28-38`

The type split is the right idea and resolves the `pt-BR` hazard. But `WhisperLanguage` is a closed
enum with 9 cases, while `README.md:70` states: "The system will ultimately handle the multilingual
languages supported by the selected WhisperKit model." Whisper supports roughly 99 languages.

As written, transcribing German, French, Russian, Hindi, Arabic, Vietnamese, or Thai requires a
source-code change. Review #1 asked for "a validated Whisper language token drawn from the known
set" — this over-corrected from an unvalidated string to a set that excludes ~90 supported
languages.

Recommendation: a `struct` wrapping a validated lowercase token checked against the full Whisper
language set, with the current nine as named statics for convenience. Keeps validation, restores the
documented capability.

### 1.5 The validation asymmetry: input is typed, output is not

`SpeechRecognizing.transcribe(_:language:)` now takes a validated `WhisperLanguage`
(`Protocols.swift:31`), but `RecognizedSegment.language` is still the unvalidated `LanguageTag`
(`TranscriptModels.swift:57`). So the **detected** language — the one that actually arrives from
WhisperKit at runtime and drives behavior — bypasses the new type entirely.

This directly undermines the English-bypass added at `TranslationPipeline.swift:52`:

```swift
if segment.language == .english {
```

`LanguageTag` equality is raw-string equality. If the not-yet-written WhisperKit adapter produces
`LanguageTag("EN")`, `LanguageTag("en-US")`, or `LanguageTag("English")`, the bypass silently fails
and English audio gets sent to the translator to be "translated" into English. The unwritten adapter
boundary is exactly where this lands, so it is worth deciding the normalization rule before writing
it.

### 1.6 English bypass fights the code-switching commitment made in the same commit

`TranslationPipeline.swift:52-57` bypasses translation for any segment whose language is English.
The same commit added to `README.md:264`: "The tracker must also support mixed or code-switched
speech rather than forcing a permanent single-language latch, particularly for Tagalog-English
conversations."

Whole-segment bypass is the coarsest possible response to code-switching. A Taglish utterance that
Whisper labels `en` — common, since Taglish is heavily English-lexified — passes through
untranslated with its Tagalog content intact and unglossed. The user sees a "translation" that is
partly a foreign language.

Also, `README.md:265` says English segments "bypass translation **by default**," implying a toggle.
There is no flag; the behavior is unconditional.

Recommendation: decide whether bypass is keyed on language label alone, or on label plus a
confidence threshold, and make it configurable before `listen` ships.

## 2. Fixes that stopped one layer short

### 2.1 `CaptureTimeline` does not survive to the output types

`AudioChunk` and `SpeechSegment` both carry `timeline: CaptureTimeline`
(`AudioInput.swift:25,55`) — good. But `RecognizedSegment` and `TranscriptTurn`, the types that
actually reach the terminal and the JSONL, carry only `timeRange`.

The wall-clock anchor and timeline identity are therefore lost at the recognition boundary, which is
precisely where they are needed: correlating a printed turn with a `timelineDiscontinuity`
diagnostic after a device reconnect requires knowing which timeline the turn belonged to. Today it
is unrecoverable.

### 2.2 No repair policy for invalid inference timestamps

`AudioTimeRange` now throws instead of trapping — correct, and tested. But nothing in the codebase
catches it, and no policy is documented.

For a three-hour podcast, an uncaught throw at minute 90 ends the run at the same point the crash
did; it is merely catchable now. The intent of the finding was to *survive* bad model output.
Recommend naming the policy explicitly — clamp the range, keep the segment, emit a
`timelineDiscontinuity` diagnostic — and implementing it in the WhisperKit adapter.

### 2.3 The real hallucination filter is still absent, and the plumbing for it is disconnected

`TranslationPipeline.swift:128-139`

```swift
let nonSpeechLabels: Set<String> = ["music", "applause", "laughter", "silence"]
```

This catches exact bracket labels after stripping `[]()`. It does not catch `[MUSIC PLAYING]`,
`[BLANK_AUDIO]`, `[inaudible]`, `[speaking Japanese]`, or `[sound effects]` — all common — because
matching is exact.

More importantly, it does not touch the failure mode review #1 actually named: Whisper's
silence hallucinations are **fluent sentences**, not labels — `ご視聴ありがとうございました`,
`Thank you for watching!`, `字幕by…`, `Subtitles by the Amara.org community`. Every one passes the
letters check and reaches the translator.

Note also that the 2026-08-19 session explicitly cautioned against unconditional phrase blocklists;
this introduces one, just a small one.

The correct signals now exist in the type system but are not connected:

- `SpeechSegment.noSpeechProbability` exists (`AudioInput.swift:59`) — but `SpeechRecognizing`
  takes an `AudioInput`, not a `SpeechSegment`, so no-speech probability can never reach the filter.
- `RecognizedSegment.confidence` exists (`TranscriptModels.swift:60`) — and is read nowhere in the
  codebase.

The probabilistic gate the README promises (`README.md:232`) is therefore still unimplemented, and
the protocol shape currently prevents it. Worth fixing the seam before the WhisperKit adapter is
written, because the adapter is what would carry those values across.

### 2.4 `promptTokenCount` and `droppedChunkCount` are declared but never written

`DiagnosticDetails` (`DiagnosticEvent.swift:23-24`) forward-declares both. Nothing populates either.
`promptTokenCount` in particular is what makes the latency numbers in the scoreboard interpretable —
it should be written by the pipeline at the point the context is assembled.

## 4. Design question raised by the new shape

`TranslationPipeline` is an `actor` that now holds **no mutable state** — `contextTurns` is local to
the stream's `Task` (`TranslationPipeline.swift:49`). The actor isolation buys nothing, forces
`await` at every call site, and two concurrent `events(...)` calls produce two independent context
histories from one instance.

That leaves the type ambiguous: is a `TranslationPipeline` a **session** (stateful, one live stream,
continuous context, latching language state) or a **factory** (stateless, many streams)? Live capture
wants the former — language latching and rolling context are session state that has to live
somewhere. Right now it lives in a closure, which is not reachable for inspection, diagnostics, or a
future UI.

Worth deciding before the live path is built, because language latching (`README.md:264`) has no
home in the current design.

## 5. Test coverage

The gap is that the two riskiest new functions are untested:

- `boundedContext` — contains the bug in §1.3. One table-driven test catches it.
- `withTimeout` — no test that the timeout fires, that the losing task is cancelled, or that a

Suggestion: the three findings in §1.2, §1.3, and §1.6 are all cheap to pin with tests, and doing so
would have surfaced them before this commit.

## 6. Product and direction

The README changes are the right calls. Three notes:

**The milestone-2 bake-off is now correctly scoped but still under-specified.** It says "representative
priority-language samples" — for the experiment to be decisive it needs a fixed, tiny, pre-committed
sample (ten utterances in one language is enough) and a stated decision rule *before* the numbers
come in. Otherwise the result gets re-litigated. Suggest writing down in advance: "if Apple
Translation is within X of Ollama on adequacy and beats it on latency by Y, Ollama is descoped to a
benchmark candidate."

**Simultaneous-load measurement should include the failure case, not just the timing.** The interesting
outcome is not "translation took 2.8s" — it is what happens when unified memory is exhausted and
macOS starts swapping mid-session. Worth deliberately over-subscribing memory once, on purpose, to
see whether the pipeline degrades visibly or just becomes erratic. That determines whether the
"report the lag and use an explicit recovery policy" requirement (`README.md:223`) needs a hard
memory-pressure trigger.

**Operating profiles are named but not yet represented in code.** `README.md` now defines live and
offline profiles with different priorities. Nothing in `BFishCore` distinguishes them — same
pipeline, same defaults, same buffering. The place that will hurt first is buffering policy and
context limits, which should differ between the two. Worth a `PipelineProfile` value before
divergence gets hardcoded in two call sites.
