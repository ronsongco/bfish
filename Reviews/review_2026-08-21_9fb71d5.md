## 0. Disposition of review #9

Everything raised landed, plus three probes that went beyond it.

- **NFKC and WER gating** (§6) — `TextErrorRate` now uses compatibility mapping, and the
  non-space-delimited language set is handled.
- **Peak memory** (§5) — refined in `d052bdd`.
- **Confidence distribution** (§4.3) — collected and, more importantly, *used*: it became the
  hallucination probe's central evidence.
- **Per-utterance latency** (§8) — measured, with a committed repeatable harness.
- **Timestamp reconciliation** (§2, §3) — root-caused, implemented, and validated.
- **Streaming** (§8) — implemented, and it took the strategic option of the adapter owning its own
  VAD staging rather than reconciling someone else's chunker after the fact.

Three pieces of work stand out as better than what was asked for:

**The window instrumentation found the actual root cause, and it was not what I proposed.** I
inferred accumulating seek-offset drift — offsets computed from cumulative chunk lengths including
overlap. The v11 instrumentation disproved that: window 18 returned a segment at 421.20–421.68 s
when its authoritative input ended at 419.00 s, and *the next window began correctly at 419.00 s*.
Offsets were right all along; the decoder was emitting content past the end of its own input window.
That is a materially different defect with a different fix, and it was found by measurement rather
than argument.

**The hallucination probe is a genuinely valuable negative result.** Silence and pure tones both
produced the Japanese "thanks for watching" hallucination with `noSpeechProbability` 0, confidence
**0.94 and 0.9357**, and compression ratio 0.9091. No measured scalar separated them from real
speech. That kills the confidence-gate idea I suggested in review #9 §4 — high confidence on pure
silence means a threshold low enough to catch it would reject most real podcast audio. Establishing
that empirically before building on it saved the wrong design.

**The utterance latency probe answered the live-viability question.** Median 967 ms, and the
conclusion that translation is now the latency-critical stage is correct.

## 1. The reconciliation fix is validated on the file that barely exercises it

`docs/whisperkit-long-form-2026-08-21.md:36-46`

The validation reports the **8:39** fixture: 142 → 141 segments, one out-of-window removal, zero
discontinuities, 514.76 s final extent preserved.

That file had **one** discontinuity. The 65:06 fixture had **34**, magnitudes from 0.86 to 14.45 s,
and a 24.10 s overflow past media duration — and it has not been re-run. Its section in the doc
still carries only the pre-fix numbers.

So the fix is confirmed against a single instance of the simplest case. The questions it does not
answer are the ones that motivated the work:

- Do all 34 discontinuities resolve, or only the ones shaped like window 18's?
- Does the 24.10 s overflow go to zero? An overflow that large is unlikely to be one out-of-window
  segment; if it survives, the mechanism is not fully characterized.
- How many segments are removed out of 1,623, and does the removal rate look like ~34 boundaries or
  something larger, which would suggest over-removal?
- What is post-reconciliation RTF? Reconciliation is O(n²) (see §2.1), and 1,623 segments is where
  that cost first becomes visible.

This is the same pattern as review #8 §1, where the monotonicity guard was confirmed on a
single-chunk file. Re-running the 65-minute fixture costs about six minutes of compute and is the
only thing that closes the finding.

## 2. Reconciliation implementation

The approach is sound — bound content to each result's reported input extent, use word timestamps
for partial crossings, order by global media time, remove exact cross-window text only on temporal
overlap. Three issues.

### 2.1 The duplicate scan is O(n²) with an expensive constant, and the predicate is ordered backwards

`Sources/BFishWhisperKit/WhisperKitRecognizer.swift:676-682`

```swift
if let duplicate = accepted.last(where: {
    $0.windowIndex != candidate.windowIndex
        && normalizedText($0.segment.text) == normalizedText(candidate.segment.text)
        && candidate.segment.start < $0.segment.end
        && candidate.segment.end > $0.segment.start
}) {
```

`last(where:)` returns on first match, but the common case is *no* match, so it scans all of
`accepted` every time — O(n²) overall. On the 65-minute file that is roughly 1.3 million predicate
evaluations.

Worse, the ordering is inverted relative to cost. The `windowIndex` check is true for nearly every
accepted segment (they come from other windows), so it filters almost nothing. The expensive
`normalizedText` calls — NFKC compatibility mapping, lowercasing, and a filter pass over the string,
on **both** sides — then run for essentially every pair. The cheap and highly selective time-overlap
checks come last, after the work is already done.

Two changes, both free:

1. **Move the two time-overlap comparisons before the text normalization.** Duplicates only occur at
   window boundaries, so temporal overlap is extremely selective — this eliminates nearly all
   normalization calls.
2. **Hoist `normalizedText(candidate.segment.text)` out of the closure.** It is invariant across the
   entire scan and is currently recomputed on every iteration.

Together those likely turn a multi-second pass into a negligible one. Worth doing before the
65-minute re-run so its RTF is not contaminated by this.

### 2.2 `result.seekTime ?? 0` fails silently and catastrophically

`WhisperKitRecognizer.swift:600`

```swift
let windowStart = Double(result.seekTime ?? 0)
let windowEnd = windowStart + result.timings.inputAudioSeconds
```

If `seekTime` is ever nil for a window other than the first, that window is treated as starting at
0. Its true content then falls entirely outside the computed `[0, inputAudioSeconds]` extent, and
every segment in it is either clipped to nonsense or discarded as `outsideWindow`.

The whole reconciliation now depends on `seekTime` being authoritative, so a nil should be an
explicit, diagnosed condition — either a distinct diagnostic and a fallback to the previous window's
end, or a thrown error — rather than a default that silently produces a plausible-looking but wrong
transcript.

### 2.3 Exact text matching will miss partial duplicates

Duplicate removal requires normalized text equality. Punctuation and width differences are handled,
which is good. But the same audio decoded in two different windows has *different preceding
context*, so Whisper frequently produces slightly different text — a trailing particle, a dropped
filler, a different kanji choice.

`今日は天気がいい` versus `今日は天気がいいですね` will not match, so both survive and the duplicate
remains in the transcript at full length.

Worth measuring rather than assuming: count segments that overlap in time but are *not* removed. If
that number is non-trivial on the 65-minute file, exact matching is insufficient and the seam needs
a similarity threshold or word-timestamp-based trimming instead.

## 3. The hallucination blocklist targets a phrase that legitimately ends the target content

`Sources/BFishCore/Pipeline/TranslationPipeline.swift:283-301`

The evidence justifying a blocklist is strong, and the earlier caution against one (2026-08-19
session, review #2 §2.3) was correctly overridden by measurement — no scalar distinguishes these
cases. The implementation is careful: NFKC-normalized, punctuation and whitespace stripped, exact
match only, all seven project languages, and a `segment_filtered: knownHallucination` diagnostic.

The residual risk is sharper than the doc's general caveat, though, because of *which* phrase and
*which* corpus:

**「ご視聴ありがとうございました」 is the standard closing line of Japanese podcasts and videos.**
It is not an occasional coincidence — it is how the content type the project targets routinely ends.
Exact matching after punctuation stripping means a legitimate standalone closing utterance is
deleted, and VAD will very often isolate exactly that phrase as its own segment.

Exact matching does limit the blast radius: `そういうことで、ご視聴ありがとうございました` keeps its
prefix and survives. So the exposure is specifically the bare, standalone form — which is common.

The user-visible failure is silent: stdout simply loses the line. The `segment_filtered` diagnostic
records it, but only someone reading the JSONL would know.

Mitigations worth considering, roughly in order of cost:

- Require corroborating evidence before suppressing — the segment is the sole content of its window,
  or the window's audio energy is below a threshold. Both hallucination fixtures were silence and
  tones, so an energy check separates them cleanly from a real spoken closing line.
- Suppress only outside the final N seconds of media, since the legitimate use is a closing line.
- Mark rather than delete: keep the segment with a flag so the terminal can show it dimmed or
  annotated, leaving the judgment to the reader.

The first is the most robust and directly matches the evidence already collected.

## 4. The latency data supports a model, and one implication worth acting on

`docs/whisperkit-utterance-latency-2026-08-21.md`

Fitting the five points gives a clean linear relationship:

**latency ≈ 640 ms + 75 ms per second of audio** (3 s→856, 4 s→894, 5 s→967, 6 s→1050, 8 s→1222).

That is more useful than the median, because it predicts any utterance length and separates the two
cost components. Worth recording in the doc.

The dominant term is the **~640 ms fixed cost**, and its likely cause has a design consequence:
Whisper's encoder always processes a 30-second mel window regardless of how much real audio it
contains (confidence ~80%). A 3-second utterance pays a full 30-second encoder pass. The ~75 ms/s
marginal term is then decoder work.

Two implications:

**The segmenter's target utterance length is now a measured tradeoff.** At 3 s the cost is 856 ms
for 3 s of audio; at 8 s it is 1222 ms for 8 s. Shorter utterances give faster time-to-first-output
but substantially worse efficiency — roughly 28% of real time at 3 s versus 15% at 8 s. When the VAD
segmenter is built for live mode, this curve should inform its minimum utterance duration rather
than being discovered later.

**Batching is available as an optimization lever.** If the fixed cost is encoder padding, packing
several short utterances into one 30-second window costs one encoder pass instead of several. That
trades latency for throughput, which is the wrong direction for live captioning but the right one if
WhisperKit and the translation model start contending for the ANE. Worth knowing it exists before
the concurrency experiment.

## 5. Smaller items

**Post-reconciliation RTF is unreported.** The 8:39 validation records segment counts and extents
but not recognition wall time. Reconciliation adds a pass, and §2.1 makes that pass superlinear. One
number closes it.

**The streaming validation is qualitative.** "Approximately three minutes of timestamped source
output had been delivered well before recognition completion" is the right observation, but
time-to-first-segment is the metric that matters for the user experience claim, and it is
measurable — it would also be directly comparable to the live budget from §4.

**Music and real-world non-speech remain untested.** The doc says so explicitly and correctly. The
probes used digital silence and synthesized tones, which are the easiest possible non-speech. Real
music with vocals, applause, and speech-over-music are the cases where the blocklist will be tested
against content that legitimately contains speech-like structure.
