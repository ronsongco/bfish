## 1. The smoke test's two most important checks ran on an input that cannot fail them

This is the main finding of this review.

The fixture is **5.835 seconds** of synthesized speech. `chunkingStrategy: .vad` produces chunks on
the order of 30 seconds, so this file almost certainly produced a **single chunk and a single
`TranscriptionResult`**.

Two guards added specifically in response to review #6 were then reported as confirmed:

| Recorded result | What it actually exercised |
|---|---|
| "Segment timestamps: monotonic, with no repair or discontinuity diagnostics" | Monotonicity **within** one chunk. The invariant exists to catch chunk-relative offsets across a boundary — no boundary existed. |
| "Source media duration and the SDK task-input sum agree within approximately 0.00006 seconds" | One chunk covering the whole file. The concern was VAD padding, overlap, or silence-trimming **accumulating across chunks** — nothing accumulated. |

Both results are true and both are uninformative about the risk they were built for. The
`whisperkit-preflight.md` claim that "WhisperKit 1.1 applies VAD and incremental-loading seek
offsets" is still resting on documentation review, not observation.

This is worth naming because the two checks now look validated in the record, and a future reader —
including a future session — will reasonably read the smoke doc as having cleared them.

**Recommendation:** before the `large-v3` quality run, do one multi-chunk pass — a fixture of at
least 90 seconds, ideally with two or three seconds of silence at ~30s and ~60s so VAD is forced to
split. Then assert three things from the JSONL alone: segment starts increase monotonically across
the whole file, the last segment's end is close to media duration, and
`sdkInputAudioSeconds` versus `audioDurationSeconds` still agree. That converts both guards from
untested to tested at the cost of one longer fixture.

## 2. RTF 0.062 does not generalize, and the number that decides the live design is not this one

The cached run reports RTF 0.062 and the doc concludes the path is "comfortably faster than real
time on this host for a short synthetic fixture" — correctly hedged. Making the hedge explicit,
because this number will be quoted later:

Every dimension of the fixture is the favourable extreme — `tiny` (the smallest model), 5.8 seconds
(short enough that fixed overheads dominate differently than on long files), clean synthesized
speech, one speaker, no background, no disfluency, and no concurrent workload.

The measurement that actually determines whether the live concept is viable is **`large-v3` RTF on
60+ seconds of real speech with a translation model resident**. `large-v3-v20240930_626MB` is
roughly an order of magnitude larger than `tiny`. RTF does not scale linearly with parameter count
on Apple Silicon — ANE utilization, memory bandwidth, and fixed per-file overhead all break the
proportion — so I will not put a number on it. But the plausible range spans "still comfortably
real-time" to "approximately real-time before contention," and only the upper half of that range is
compatible with the 2–4 second end-to-end target once an LLM is sharing the machine.

That single measurement is the highest-information experiment remaining in the project, and it is
cheap now that the adapter works. It should come before, not after, the translation bake-off — if
`large-v3` is near real-time under load, the live design changes (smaller model, or Whisper-direct
with no LLM), and the bake-off's premises change with it.

## 3. Model initialization dominates, with a consequence for the benchmark harness

Cached run: 2.72 s resolution + 4.61 s load = **7.33 seconds of setup for 0.36 seconds of
recognition** — roughly 20:1. The doc notes this and flags persistent-process measurement as
important, which is right.

The under-stated consequence is for the scoreboard. The planned harness runs many models across many
fixtures. At `tiny`'s ~7 s load, a sweep of eight candidate models is already a minute of pure load
time per pass; `large-v3` at 626 MB will load substantially slower. Two implications worth deciding
before building the harness:

- The harness should be a **persistent process** that loads each model once and runs the whole
  fixture set against it, rather than a per-fixture CLI invocation. The recognizer already caches
  the engine per instance, so this is a harness-shape decision, not a code change.
- Cold-load should be measured **deliberately once per model** rather than incidentally on every
  run, which is what `README.md:441`'s "cold-load and warm-run measured separately" actually
  requires.

## 4. The fixture class is an upper bound, not a sample

The doc already commits to "representative legally usable speech rather than synthesized speech
alone" for the next run. Reinforcing why, because it changes how the current result should be read:

macOS Kyoko TTS is perfectly enunciated, noise-free, disfluency-free, single-speaker, and
consistently paced. It is the easiest input that exists, and it is also the one input class that
will never occur in the actual use case — podcasts, calls, and application audio are none of those
things.

So the quality observation is more pointed than the doc frames it. `tiny` mis-recognized 音声 as
本生 **on clean synthesized speech**. That is not merely "tiny is a development model"; it is a
data point that the error floor on real material will be materially worse. The result is an upper
bound on quality, and the RTF is a lower bound on cost.

FLEURS, already adopted at `README.md:433`, gives real read speech with reference transcripts across
all seven project languages — it is a better next fixture than another synthesized clip, and it
makes §5 below computable.

## 5. Quality was compared by eye, and there is no scoring code

The smoke doc's quality finding is an anecdote: one substitution, spotted by reading. That is
appropriate for a smoke test and will not scale to the model comparison.

The WhisperKit model evaluation (`README.md` milestone 3) needs a character or word error rate
against a reference transcript, and nothing in the repository computes one. For CJK languages CER is
the appropriate metric — WER is not meaningful without word segmentation, which is exactly the
failure mode `本生` vs `音声` represents (a two-character substitution inside an unsegmented run).

Worth scaffolding a small CER/WER utility alongside the next fixture, so the `large-v3` run produces
a number rather than an impression. Without it, milestone 3's "compare candidate WhisperKit models"
has no comparison mechanism.

## 6. Recognition metadata is still missing from the JSONL artifact

The smoke doc's own conclusion flags this, and I confirm it: `TranscribeCommand` emits
`recognition_completed` carrying `audioDurationSeconds`, `realTimeFactor`, and
`sdkInputAudioSeconds`, but **not the detected language or `languageConfidence`**.

The doc records "Detected language: Japanese (`ja`)" — but that came from the human-readable
transcript header, not the machine-readable stream. From the JSONL alone, a consumer cannot
reconstruct which language was selected or how confident detection was.

Both values are already on every `RecognizedSegment`, and both are privacy-safe by the project's own
standard — a language token and a probability are not transcript content. Adding them to the
`recognition_completed` details is small and directly enables the confidence-gating decision
deferred at `docs/whisperkit-preflight.md:117`, since that decision needs observed confidence
distributions to set a threshold.

## 7. Smaller items

### 7.1 The smoke test is not reproducible from the record

`docs/whisperkit-smoke-2026-08-21.md:11` notes the fixture and raw run files were temporary and
uncommitted, which is a reasonable call for audio. But the synthesized fixture is *generated*, so
the generator is the artifact worth keeping: the doc records the text and the Kyoko voice, but not
the exact `say` invocation, output format, sample rate, or any conversion step.

One command line in the doc makes the run repeatable on any Mac without committing audio.
`README.md:439` requires runs to record enough metadata to be reproduced; this one currently is not.

### 7.2 Cold runs will carry ~100 `model_status` lines

De-duplication reduced the download progress to one event per changed integer percent, which is the
right fix. It still means up to 101 `model_status` events per cold run in the artifact — 31 stderr
lines for `tiny`, and proportionally more for a 626 MB model.

Not wrong, and they are properly typed and parseable. Noting only that a harness aggregating many
runs will want to filter them, and that the run-manifest design should expect progress events to
outnumber substantive ones.

### 7.3 `AVAudioFile` duration — narrower risk than expected

I checked whether the new duration gate could reject files WhisperKit could otherwise handle. Tested
`AVAudioFile(forReading:)` against AIFF, audio-only M4A, and audio-only MP4 containers: all three
open correctly and report identical duration. So the common cases are fine.

The residual risk is video containers with an audio track (`.mp4`/`.mov` from a screen recording or
a downloaded talk), which `AVAudioFile` is not designed to open and which `AVURLAsset` handles.
Untested here. Given the stated sources are podcasts and routed application audio, this is a low
priority — but `invalidAudioDuration` now fails *before* model load, so if it does occur it will
read as "bfish cannot handle this file" rather than "use a different container."

## 8. Test coverage

30 passing. The three new tests map one-to-one onto review #7's findings, and
`modelStatusesProduceParseablePrivacySafeJSONL` is the right shape — it asserts the property the
finding was about (every emitted line parses as JSON) rather than a specific string.

On §1: `mapperPreservesTimelineAndReportsNonMonotonicResults` does construct exactly the
chunk-relative case — a second `TranscriptionResult` whose segment starts at 2 after the first ended
at 11 — and asserts the `timeline_discontinuity` diagnostic fires through `map`. So the unit-level
behaviour is properly pinned, and the invariant would catch a real chunk-offset bug.

What remains outstanding in §1 is therefore narrower than "untested": the *guard* is tested, but the
*SDK's actual behaviour* has not been observed across a chunk boundary. The multi-chunk fixture is
still worth running, but the outcome to expect is confirmation rather than discovery, and if the
guard ever fires on real audio it will be a genuine SDK finding rather than an adapter bug.

## 9. Sequencing

The adapter is working and the diagnostics stream is now genuinely machine-readable — that is real
progress, and the smoke test was the right thing to do.

Recommended order for what comes next, by information value:

1. **`large-v3` on a 90+ second real-speech fixture.** Settles §1 (multi-chunk guards), §2 (the RTF
   number that decides the live design), and §4 (real-material quality) in one run.
2. **Add language and confidence to the JSONL** (§6) before that run, so it produces a complete
   artifact rather than one needing a second pass.
3. **A CER utility** (§5) so the run yields a number.
4. Then the translation bake-off, whose premises depend on 1.

The one thing I would avoid is running the bake-off before the `large-v3` RTF measurement. The
bake-off's decision rule is latency-based, and if speech recognition alone consumes most of the
latency budget on the accuracy model, the rule's thresholds are being set against the wrong baseline.
