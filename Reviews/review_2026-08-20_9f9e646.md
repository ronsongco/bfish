## 1. Cantonese detection aborts the entire transcription — verified

`Sources/BFishCore/Domain/LanguageTag.swift:53-62`, `Sources/BFishWhisperKit/WhisperKitRecognizer.swift:70-73`

Diffed the SDK's language table against `WhisperLanguage.supportedTokens`:

```
SDK unique tokens:  100
bfish tokens:        99
in SDK but NOT accepted by bfish:
yue
```

`yue` is the exact and only gap. It is a first-class token in the SDK —
`Sources/WhisperKit/Core/Models.swift:1442` maps `"cantonese": "yue"`, and line 1307 groups it with
`zh`, `ja`, `th`, `lo`, `my` for non-space-delimited text handling.

So when `detectLanguage` returns `yue` on Cantonese audio:

```swift
guard let detected = WhisperLanguage(rawValue: detection.language), detected != .automatic else {
    throw WhisperKitRecognizerError.unsupportedLanguage(detection.language)
}
```

the whole transcription throws before any audio is processed. No partial output, no fallback.

Failure scenario: a Cantonese-language podcast, or a Mandarin recording where the opening 30 seconds
is Cantonese, fails outright. Mandarin is a primary project language and Cantonese material is
plausible in the same corpus.

Two fixes, and the second matters more than the first:

1. Add `yue` to `supportedTokens`.
2. **An unrecognized detected token should degrade, not abort.** Emit a diagnostic and either fall
   back to a configured default or carry the raw token through, rather than failing a two-hour file
   because of one string. Aborting an entire run on a single unexpected value is the same failure
   shape as the original `precondition` finding from review #1 — the codebase has consistently moved
   away from it everywhere else.

## 2. Language is latched from a 30-second window with no confidence gate

`Sources/BFishWhisperKit/WhisperKitRecognizer.swift:69-87`

`detectLanguage(audioPath:)` inspects only the first 30 seconds — the preflight doc states this at
line 72 — and the result is then latched into `DecodingOptions(language:detectLanguage: false)` for
the **entire file**.

If the first 30 seconds is an English intro, a music sting, silence, or a cold open in another
language, every subsequent segment is transcribed under the wrong language for the whole recording.
For podcasts and interviews — the stated offline use case — an English or musical intro is the norm,
not the exception. I'd rate this the most likely practical failure on real material.

The sharper problem: `languageConfidence` is captured at line 75 and then **never acted on**. It is
recorded onto every segment for the record, but nothing checks it before latching. A detection at
probability 0.28 latches exactly as firmly as one at 0.99.

`README.md:264` promises a language "latched until repeated contrary evidence crosses a defined
threshold." The adapter has neither a threshold nor any contrary-evidence path.

Minimum fix: emit a diagnostic when detection confidence falls below a threshold, and expose
`--min-language-confidence`. Better: sample `detectLanguage` at several offsets through the file and
take a majority, which is cheap relative to full transcription and directly addresses the intro
problem.

## 3. Recognition is batch-only, so the first real command emits nothing until the file finishes

`Sources/BFishCore/Pipeline/Protocols.swift:31`, `Sources/bfish/BFishCommand.swift:60-72`

`SpeechRecognizing.transcribe` returns a `SpeechRecognitionOutput` holding a complete
`[RecognizedSegment]`, and `TranscribeCommand` awaits the whole thing before writing its first line.
It also bypasses `TranslationPipeline` entirely, so the streaming machinery built over reviews #1–#3
is not on this path at all.

For a two-hour podcast: no output for the entire run, and every segment retained in memory until the
end. `README.md:490` states for the offline profile that "incremental output is still required so
long recordings do not accumulate entirely in memory."

This is review #1 §2.4 resurfacing one layer down. The pipeline was made streaming; the recognition
boundary underneath it is still batch, so streaming cannot actually reach the user. Changing
`SpeechRecognizing` to yield segments as they are produced is a protocol change — cheaper now, with
one implementation, than after Ollama and live capture are built against it.

Related naming note: `--incremental` bounds audio *loading* memory only. A user reading the flag
alongside a long-file workflow will reasonably expect incremental *output*.

## 4. Real-time factor cannot be computed from what the code emits

`Sources/BFishWhisperKit/WhisperKitRecognizer.swift:189-198`

`timingSummary` sums WhisperKit's internal per-result timings across chunks. Summed `fullPipeline`
is total compute, not elapsed wall-clock, and nothing measures elapsed time or audio duration.

`docs/whisperkit-preflight.md:105` lists "full pipeline time and real-time factor" among the values
the first smoke test must record. RTF is `elapsed / audio_duration`; neither operand is produced.
Model download and load time (line 103) is likewise not separated from transcription time, though
`README.md:441` requires cold-load and warm-run measured separately.

Since the milestone-2 decision rule is latency-based, this is a measurement gap arriving exactly
when measurement begins. Add wall-clock elapsed around the call, audio duration, derived RTF, and
model-load as its own `StageTiming`.

## 5. Model download is silent and unbounded

`Sources/BFishWhisperKit/WhisperKitRecognizer.swift:103-117`

`loadEngine()` creates the download directory and calls `WhisperKit(config)` with no progress
reporting and no timeout. On first run the CLI produces no output while fetching a model — roughly
40 MB for `tiny`, 600 MB+ for the `large-v3` accuracy baseline. On a slow connection that is minutes
of apparent hang with no way to distinguish it from a deadlock.

`README.md:369` requires that "model-loading progress should be written to standard error."
WhisperKit exposes a progress callback for this.

## 6. VAD chunk timestamps are unverified, and the repair path cannot catch the failure

`Sources/BFishWhisperKit/WhisperKitRecognizer.swift:86,131-149`

`chunkingStrategy: .vad` causes WhisperKit to return multiple `TranscriptionResult` values. The
mapper iterates `results` then `result.segments`, appending in order and carrying `fallbackStart`
forward, but **never applies a per-chunk offset**.

If segment `start`/`end` inside a chunked result are chunk-relative rather than file-absolute, the
emitted transcript will have timestamps that restart near zero at every chunk boundary.

The important part: `AudioTimeRange.repairing` would **not** flag this. Each chunk's values are
individually finite, non-negative, and correctly ordered — they are only wrong relative to the file.
`fallbackStart` is consulted only on the non-finite path. So a real corruption would pass every
existing guard silently and land in the transcript looking plausible.

I cannot resolve whether WhisperKit 1.1.0 applies the seek offset for `.vad` chunking without
running a model, so this is flagged as *verify*, not *defect*. It is the single highest-value thing
for the first smoke test to check, and the preflight doc's item "raw and repaired segment
timestamps" (line 107) does not specifically call out cross-chunk monotonicity.

Cheap structural defense, worth adding regardless of what the smoke test finds: assert monotonicity
in the mapper — segment *N* start ≥ segment *N−1* start — and emit the existing
`timelineDiscontinuity` diagnostic when violated. That converts an invisible corruption into a
reported one.

## 7. Smaller items

### 7.1 Out-of-range probability is clamped silently

`WhisperKitRecognizer.swift:177` clamps `noSpeechProbability` into `0...1`, and the test at
`WhisperKitRecognizerTests.swift:22` feeds `1.2` and asserts `1`.

Every other out-of-range repair in this codebase emits a diagnostic — that is the whole design of
`timestampRepaired`. A probability outside `0...1` from the SDK is a signal that semantics changed
or something upstream is wrong; silently normalizing it discards that signal. Same treatment as
timestamps would be consistent.

### 7.2 `confidence` is not comparable across languages

`WhisperKitRecognizer.swift:175` stores `exp(avgLogprob)` — a per-token geometric mean probability,
not a probability of correctness. It is not comparable across model sizes, and it is systematically
different across scripts because CJK tokenization produces different per-token distributions than
Latin script.

The preflight doc hedges correctly by calling it a "recognition confidence estimate." Worth
recording explicitly that any future gate on `confidence` must be calibrated per language, or it
will silently behave differently for ja/zh than for es/it — which would then be misread as a
transcription-quality difference.

### 7.3 Audio is decoded twice

`detectLanguage(audioPath:)` then `transcribe(audioPath:)` each load the file. Minor, but more
noticeable on long files, and it partly undercuts `--incremental`'s bounded-memory intent.

### 7.4 `CaptureTimeline(startedAt: Date())` means processing time in file mode

`WhisperKitRecognizer.swift:65` anchors the timeline to "now," which is when the file was
*processed*, not when it was recorded. Defensible, and it does give a stable session anchor — but
live sessions will anchor to actual capture start, and the two will eventually be compared. Worth
one line in the docs stating which semantic applies in which mode.

### 7.5 No `unload()` on the recognizer

The actor holds `whisperKit` for the process lifetime with no release path. Fine for a one-shot CLI;
it becomes relevant for a UI target that switches models.

## 8. Test coverage

22 passing, up from 20. The two adapter tests are well chosen: the mapper test drives NaN start,
untrimmed text, an out-of-range `noSpeechProb`, and asserts the repair diagnostic — that is the
right unit to test without a model, and it directly exercises the seam.

Gaps matching findings above:

- No test that an unknown detected token is handled (§1) — one test with `"yue"` would have caught it.
- No test for multi-result mapping (§6). The mapper's `results` loop and `fallbackStart` chaining are
  entirely uncovered; every existing test calls `mapSegment` directly, never `map`.
- No test asserting one timeline across multiple results, though the preflight doc lists it at
  line 95 as a pre-model test.

The preflight doc's own test list (lines 92–97) contains four items not yet implemented: unknown
detected-language rejection, one-timeline-per-file, and non-file input rejection. Worth closing
those before the smoke test, since they are all model-free.

## 9. Sequencing note

The three findings that should land **before** the first real-audio smoke test are §1 (Cantonese
abort), §4 (RTF measurement), and §6's monotonicity assertion — because the smoke test is supposed
to *produce* the timestamp and latency evidence, and currently it would either abort on some inputs,
be unable to compute the headline number, or fail to notice the one corruption class its guards
cannot see.

§2 (language latching) and §3 (batch-only output) are better addressed after the smoke test, when
there is real evidence about how detection behaves on actual material and how long a real file
takes.
