## 1. New observations

All three are minor. Nothing in this commit introduced a regression.

### 1.1 Locale region-subtag validation accepts non-ASCII numerals — verified

`Sources/BFishCore/Domain/LanguageTag.swift:58-68`

```swift
case 3:
    return isASCIILetters(value) || value.allSatisfy(\.isNumber)
```

`Character.isNumber` is true for any Unicode `N*` category, not just ASCII digits. The adjacent
`case 5...8` branch explicitly requires `$0.isASCII`; this branch does not. Verified against the
predicate as written:

| subtag | accepted | ASCII |
|---|---|---|
| `BR` | yes | yes |
| `419` | yes | yes (correct — UN M.49) |
| `٣٣٣` (Arabic-Indic) | **yes** | no |
| `ⅢⅢⅢ` (Roman numeral, `Nl`) | **yes** | no |

BCP-47 region subtags are two ASCII letters or three ASCII digits. So `SessionLocale("pt-٣٣٣")` is
accepted, normalized to itself, and would render in the terminal header.

Consequence is cosmetic — it is a display tag — but the fix is adding `$0.isASCII` to that branch,
matching what the 5–8 branch already does.

### 1.2 `TranscriptTurn.init` reintroduces a silent default for a session-scoped field

`Sources/BFishCore/Domain/TranscriptModels.swift:149`

```swift
public init(segment: RecognizedSegment, englishText: String?, sessionLocale: SessionLocale? = nil)
```

A caller that omits `sessionLocale` silently gets `nil`, and `TerminalTranscriptFormatter` falls
back to `turn.language.rawValue` — so `pt` prints where `pt-BR` was configured, with no error.

This is the same shape as two problems already fixed in this codebase by the opposite choice:
`timeline:` had its default removed in `8e4caf5`, and `profile:` was made required in the same
commit, specifically so omission becomes a compile error rather than a silent fallback.

The pipeline is currently the only production constructor, so exposure is low. Noting it because
the project has twice decided this trade the other way, and consistency is worth more than the
convenience here.

### 1.3 The `noLetters` case name now describes the wrong thing, at no compatibility benefit

`SegmentFilterReason.noLetters` still carries raw value `"noLetters"` while its implementation is
now "neither letters nor numbers." `docs/diagnostics-schema.md` documents this honestly and retains
the name "for schema compatibility."

Worth checking that premise: schema v3 was introduced one commit earlier, `Benchmarks/Runs/` is
gitignored and empty, and no run artifacts exist anywhere in the repository. There is currently
nothing to be compatible *with*.

So the project is accepting a permanently misleading identifier — in the Swift enum, in the JSONL
raw value, and in a doc note that has to explain the discrepancy forever — in exchange for
compatibility with zero existing records. Renaming to something like `noContent` while the cost is
zero seems clearly better than carrying the explanation indefinitely. This is the last moment it is
free.

## 2. Open items, unchanged

### 2.1 Head-of-line blocking and lag instrumentation — third review, unaddressed

Raised in review #3 §1.6, re-raised in review #4 §2.1, unchanged again. Still strictly serial
translation (`TranslationPipeline.swift:83-88`), still a 15-second live timeout against a 2–4 second
target, still no pending-translation bound, queue-depth diagnostic, or recovery policy.

Rather than restate the analysis a fourth time: after two commits that fixed everything else raised
alongside it, the most likely explanation is that this is being **deliberately deferred** until live
capture exists — which is a defensible call, since the serial loop is correct for the file path that
milestone 2 actually needs.

If that is the decision, it is worth recording as one. The specific risk in leaving it implicit is
the dependency noted in review #4: the memory-oversubscription experiment at `README.md:513` is
designed to observe whether degradation is *visible*, and it cannot answer that question against a
pipeline with no lag instrumentation. So the deferral is fine, but it should be sequenced *before*
that experiment rather than after it, and the README's backpressure requirements
(`README.md:223-225`) currently read as satisfied when they are not yet implemented.

Suggested resolution: one line in the milestone list placing lag/queue-depth diagnostics in
milestone 5 or 6, explicitly ahead of the oversubscription run.

### 2.2 Session lock has no diagnostic or recovery path

Review #3 §2.3, review #4 §2.2. Unchanged, still low severity while the only callers are tests and
`process(...)`.

## 4. Note on review cadence

Five reviews across one day have converged: every defect from reviews #1–#4 is either fixed or,
in one case, an open design decision. What remains is small — two naming/consistency items, one
validation branch, and one deferred concurrency decision.

The scaffold is now in good shape and further review of it will have diminishing returns. The
highest-value next review is **after the WhisperKit adapter lands**, because that is where the
unvalidated assumptions actually live: timestamp repair against real model output, language-token
normalization against what WhisperKit actually emits for detected languages, `noSpeechProbability`
and `languageConfidence` plumbing, `CaptureTimeline` assignment, and the first real latency numbers.
Every one of those is currently a contract with no implementation behind it.

Reviewing the adapter and the milestone-2 bake-off results together would be more useful than
another pass over the domain types.
