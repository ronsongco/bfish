# bfish Review — 2026-08-20

Reviewed at commit `08f7d7f Scaffold native Swift foundation`.

Scope: full `README.md`, all nine source files, both test files, `Scripts/package-local.sh`,
`Resources/bfish-Info.plist`, `.gitignore`, and the five `.session/` snapshots. Items already
triaged in the 2026-08-19 architecture review are not re-raised here.

Overall assessment: the documentation is unusually thorough and the domain modeling instincts are
right — immutable source text, translation-only model responses, optional speaker identity,
protocol boundaries. The findings below are not sloppiness. They are places where the scaffold's
*shape* commits to something the live product cannot honor, plus two plan-level bets I think are
wrong.

---

## 1. Code defects to fix before WhisperKit lands

### 1.1 `precondition` on model-derived timestamps will hard-crash in release

`Sources/BFishCore/Domain/TranscriptModels.swift:8-9`

```swift
precondition(start >= 0, "Audio start time must not be negative")
precondition(end >= start, "Audio end time must not precede start time")
```

`precondition` is **active** in `-O` release builds — only `assert` is stripped — and
`Scripts/package-local.sh:5` defaults to `release`. WhisperKit segment timings are model output:
non-monotonic and NaN timings are a known Whisper edge case. NaN fails `end >= start`, so it traps
too. This crashes the CLI 90 minutes into a podcast with no recovery.

A type constructed from untrusted inference output needs a throwing or clamping initializer at the
adapter boundary, not a trap.

Related asymmetry: `AudioTimeRange` is `Codable`, and the synthesized `init(from:)` assigns stored
properties directly, bypassing both preconditions. The invariant is enforced in memory and
unenforced over JSONL. Since re-scoring old benchmark runs is an explicit project goal, that
asymmetry matters.

### 1.2 The pipeline violates the README's own error-isolation requirement

`Sources/BFishCore/Pipeline/TranslationPipeline.swift:24-27`

`README.md:245` states: "A recoverable Ollama failure should preserve and print the source
transcript." The pipeline has no `do`/`catch` and no timeout — one failed translation throws and
discards every turn accumulated so far.

Consequence: `TranscriptTurn.englishText` is `String?` and
`Formatting/TerminalTranscriptFormatter.swift:12` has a `<translation unavailable>` branch, but
**nothing in the codebase can currently produce either.** The optionality and that branch are dead
code today.

This is the one place where implemented behavior directly contradicts a stated requirement rather
than merely not-yet-implementing it.

The other half is the missing timeout: `URLSession`'s default resource timeout is effectively
unbounded, so a wedged Ollama generation wedges the whole process with no diagnostic output.

### 1.3 `runCommand` can deadlock

`Sources/bfish/Doctor.swift:108-124`

`waitUntilExit()` is called before `readDataToEndOfFile()` on a single shared pipe. If a child ever
writes more than the ~64KB pipe buffer, the child blocks on write and the parent blocks in wait.

`xcodebuild -version` is tiny so this is invisible today, but this helper will obviously be reused
for `ollama list`, model pulls, or `system_profiler`. Read to end first, then wait.

### 1.4 Doctor reports PASS for the exact condition it exists to catch

`Sources/bfish/Doctor.swift:74-76`

```swift
.first { $0.hasPrefix("Authority=") || $0.hasPrefix("Signature=") }
```

Ad-hoc signing emits `Signature=adhoc`, so this returns PASS. Meanwhile `README.md:57` and the
packaging script's own stderr warning (`Scripts/package-local.sh:21`) both say ad-hoc will not
preserve TCC grants across rebuilds.

The 2026-08-19 session snapshot records "doctor reported PASS for ... ad-hoc signing" as a success.
It is not. Ad-hoc should be `WARN`, with the resolved identity name surfaced in the detail string.

### 1.5 Doctor's Ollama check misses the failure mode that will actually hurt

`Sources/bfish/Doctor.swift:88-106`

- Endpoint is hardcoded to `127.0.0.1:11434` while `README.md:375` lists it as configurable.
- `OLLAMA_HOST` — the standard way users relocate Ollama — is ignored.
- "22 installed model(s)" is not a useful signal; those could all be embedding models.

More importantly, the failure that will actually break this project is **unified memory**, not
reachability: `large-v3` + SpeakerKit + a 7-8B q4 translator running concurrently. Doctor should
report physical RAM and free disk, because that is the check that predicts whether the design is
viable on the target Mac at all.

### 1.6 `DoctorReport` is already `Codable` but there is no `--json`

Trivial to add, and it makes `doctor` usable as a precondition check inside the benchmark harness
the plan requires.

### 1.7 Version has two sources of truth

`Sources/BFishCore/BFishCore.swift:3` says `0.1.0-dev`; `Resources/bfish-Info.plist:18` says
`0.1.0`. These will drift, and benchmark run metadata is supposed to record the exact build.

## 2. Where the types commit to something the live product cannot honor

These are the highest-value items. All are cheap now and expensive once WhisperKit and Core Audio
are wired in.

### 2.1 `AudioFrame.samples: [Float]` forces the allocation the architecture forbids

`Sources/BFishCore/Domain/AudioInput.swift:11`

`README.md:222` states live capture must not block the real-time audio callback. A Swift
`Array<Float>` is a heap allocation — constructing an `AudioFrame` inside a Core Audio IOProc is a
`malloc` on the real-time thread, which is precisely the prohibited operation.

The domain type as designed makes the correct implementation awkward and the incorrect one natural.
The right shape is a pre-allocated ring buffer at the C boundary, with `AudioFrame` materialized on
the **consumer** side, outside the callback.

### 2.2 `AsyncThrowingStream` with no buffering policy defeats the backpressure design

`Sources/BFishCore/Pipeline/Protocols.swift:4,8`

`AsyncThrowingStream`'s default buffering policy is `.unbounded`. The README's entire backpressure
section (bounded queues, visible lag, explicit recovery policy, `README.md:220-224`) therefore has
zero representation in the type signature, and each implementation will silently pick its own
policy.

Recommended: express `.bufferingNewest(n)` at the boundary, and add a first-class dropped-frame
counter. `README.md:224` requires that any decision to skip stale audio be visible in diagnostics —
today there is nowhere to report drops except an untyped `metadata` string key.

### 2.3 `SpeechSegmenting` emits bare `[Float]`, discarding the time range

`Sources/BFishCore/Pipeline/Protocols.swift:7-9`

You cannot timestamp a segment produced by this protocol. It also drops sample rate and channel
count (which `AudioFrame` carries *per frame*, implying format can change mid-stream — unhandled
anywhere), and it drops the **reason** for the cut: silence vs. max-duration vs. quality gate.

That reason is exactly the signal needed when debugging segmentation against golden fixtures.
This should emit a struct: normalized mono samples + sample rate + `AudioTimeRange` + cut reason.

### 2.4 `TranslationPipeline` is a batch API for a streaming product

`Sources/BFishCore/Pipeline/TranslationPipeline.swift:18`

```swift
public func process(_ input: AudioInput, language: LanguageTag = .automatic) async throws -> [TranscriptTurn]
```

Returning an array after completion is unimplementable for live capture, and for a 3-hour podcast
file it means unbounded memory growth with no output until the whole file finishes.

Note also that `AudioCapturing` and `SpeechSegmenting` are declared but wired to nothing — the
"pipeline" currently covers only the file path.

Recommendation: make the primary API `AsyncStream<TranscriptTurn>` **now**, and define the array
version as a reduction over it. Today's four tests then survive milestone 6 instead of being
rewritten.

### 2.5 `LanguageTag` conflates a Whisper token with a locale tag

`Sources/BFishCore/Domain/LanguageTag.swift`

Highest-confidence design smell in the codebase (~85%).

`LanguageTag` is an unvalidated string wrapper, and `.brazilianPortuguese = "pt-BR"` sits next to
`.japanese = "ja"` with identical type. `SpeechRecognizing.transcribe(_:language:)` takes a
`LanguageTag`, so passing `.brazilianPortuguese` typechecks and then fails or silently falls back at
the WhisperKit boundary.

`README.md:85` already knows this and explains it in prose — but prose does not stop the call site.
Also `LanguageTag("Japanese")` and `LanguageTag("JA")` are equally accepted today, and both are
wrong for WhisperKit.

Recommendation: two distinct types — a validated Whisper language token drawn from the known set,
and a separate session display/locale tag that may carry a region subtag.

### 2.6 Timestamps have no wall-clock anchor

Everything is `TimeInterval` from an implicit zero. For live capture: what is zero, and what happens
across a device reconnect (`README.md:247` requires one) or a deliberate stale-audio skip
(`README.md:224` contemplates one)? Media time silently diverges from wall time and the JSONL
metrics become un-correlatable with anything else on the system.

Carrying both a media offset and a `Date` anchor is nearly free now. Later it touches every domain
type, the formatter, and the JSONL schema.

### 2.7 No `schemaVersion` in `DiagnosticEvent` or the planned benchmark records

`Sources/BFishCore/Diagnostics/DiagnosticEvent.swift:13`

The stated point of JSONL run artifacts is re-scoring old runs (`README.md:488`). Without a version
field, evolving the event shape corrupts history silently.

## 3. Behavior and documentation mismatches

### 3.1 The formatter does not match the documented UX

`README.md:92` shows `[00:01:42]`. `Formatting/TerminalTranscriptFormatter.swift:16-26` returns
`01:42` for 102 seconds, and only switches to `HH:MM:SS` past one hour.

Two problems: code and README disagree, and the timestamp **changes width mid-file** on any
recording over an hour — breaking column alignment and any downstream `awk`/regex consumer.

Recommendation: fixed-width `HH:MM:SS` always.

### 3.2 `Benchmarks/Runs/` is gitignored while the README requires versioned runs

`.gitignore:6` vs. `README.md:488`, which requires raw results be retained and reproducible with a
recorded corpus revision. As configured, the scoreboard has no history. `Benchmarks/README.md`
frames this as temporary — just flagging that "versioned corpus" and "gitignored runs" are in
tension and the resolution should be deliberate.

### 3.3 Two documented fixture locations

`README.md:172` places `Fixtures/` at repo root; `README.md:474` places them at
`Benchmarks/Fixtures/`. Resolve before either is populated.

## 4. Empty and garbage input gating is weaker than the design assumes

`Sources/BFishCore/Pipeline/TranslationPipeline.swift:22` filters on
`trimmingCharacters(in: .whitespacesAndNewlines).isEmpty`.

Whisper's silence failures are not empty strings. They are `ご視聴ありがとうございました`,
`字幕by…`, `Thank you.`, `[Music]`, `♪`. Punctuation-only output (`。`, `...`, `♪`) passes this
filter and gets confidently translated.

The scoreboard allocates 10 points to hallucination control on the **model** side, but the pipeline
hands the model garbage in the first place. Needed: a minimum-content gate requiring at least one
letter or ideograph after stripping punctuation and symbols, plus the README's promised no-speech
and confidence gates, before Ollama sees anything.

### 4.1 `contextLimit` counts turns, not tokens

`Sources/BFishCore/Pipeline/TranslationPipeline.swift:11,23`

Four podcast turns could be 2000 tokens; four short utterances 20. Prompt length drives latency, so
a turn-count bound makes p95 latency vary with something that is not being measured — which quietly
undermines the "warm translation latency, median and p95" scoreboard dimension (`README.md:458`).

Recommendation: bound by character count with a turn cap, and record the actual prompt token count
in the JSONL metrics so latency can be normalized across runs.

### 4.2 Context is fed only from successful turns

`Array(turns.suffix(contextLimit))` draws only from turns that translated successfully. Once error
handling exists (see 1.2), a failed segment vanishes from context invisibly, creating a
discontinuity the model cannot detect.

Separately: once diarization lands, handing the model four mixed-speaker turns as flat context is
exactly the mechanism by which models merge speakers — the behavior `README.md:272` forbids.

Decide now whether context is source-only, speaker-tagged, or restricted to the same speaker.

## 5. Direction — two plan-level bets worth reconsidering

### 5.1 The alternatives to Ollama are evaluated last, and they may win

Strongest product point in this review. Confidence the reordering is correct: ~80%.

The plan commits to Ollama as *the* translator and treats Whisper's direct-to-English task and
Apple's `TranslationSession` as fallbacks and spikes deferred to milestone 4 and later
(`README.md:200`, `README.md:262`).

But for ja/ko/zh conversational speech, a 7-14B local quantized model is not obviously better than
either alternative, and both are dramatically cheaper to build:

- **Whisper-direct** is one flag on a model already being loaded. Zero additional memory.
- **Apple `TranslationSession`** is a system framework: no memory cost, no cold-load, no contention
  with WhisperKit, and it was already verified as headless-capable in the 2026-08-19 session.

If either wins, the entire Ollama workstream — HTTP client, schema-constrained prompting, keep-alive
management, the 100-point scoreboard, the corpus — is descoped. That is weeks of work gated on the
cheapest experiment in the whole plan.

**Recommendation: run the three-way bake-off in milestone 2 on one language, not milestone 4.**

### 5.2 The 100-point scoreboard has an evaluator problem

`README.md:451` allocates 25 points — the highest weight — to meaning preservation, specified as
*human adequacy ratings*, across seven languages.

There is one evaluator. Unless the project owner reads Japanese, Korean, Mandarin, Portuguese,
Tagalog, Spanish, and Italian well enough to judge translation adequacy, the highest-weighted
dimension is unscoreable for most of the corpus — and the languages that cannot be judged are
probably the ones the tool is most needed for.

As written, the benchmark may not be executable by its only user.

**Recommended fix, which also removes the fixture-licensing blocker: FLORES-200 and FLEURS.**

- **FLORES-200** provides professionally-translated parallel text across all seven target languages.
- **FLEURS** is FLORES read aloud — paired audio + source transcript + reference English, one
  dataset, clean licensing.

Together these collapse the milestone-3 audio corpus problem and the milestone-4 text corpus problem
simultaneously, turn "human adequacy" into chrF/COMET plus targeted spot-checks, and give
cross-run comparability that self-collected clips cannot. Confidence this is the right corpus
choice: ~85%.

Caveat: FLEURS is *read* speech, so it will not exercise disfluency, code-switching, or overlapping
speakers. A small hand-built conversational set is still worth having — but it can be small and
limited to languages the owner can actually judge.

### 5.3 This may be two products

Live low-latency translation (Audio Hijack, 2-4s target, likely single speaker, robustness over
quality) and offline podcast/interview processing (diarization, `large-v3`, quality over latency, no
time pressure) have different pipelines, different model choices, and different failure tolerances.

The scoreboard's quality-leader / live-use-leader split acknowledges this, which is good. But the
corpus and the pipeline are still being designed as one thing. Worth explicitly naming which comes
first.

### 5.4 Latency is an unvalidated core assumption

The 2-4s target (`README.md:101`) assumes WhisperKit and the LLM do not contend. They share unified
memory bandwidth and the GPU/ANE.

Before building any benchmark harness, measure directly on the target Mac: `large-v3` on a 10-second
utterance, then a 7B q4 translation of that transcript, warm, with both models resident
simultaneously. If that comes to 5 seconds, the live design must change — smaller Whisper model, or
Whisper-direct with no LLM in the loop — and everything downstream shifts.

Cheap experiment, high information, and it should precede milestones 3 and 4.

## 6. Corner cases not yet addressed in the design

- **Tagalog is the worst possible case for language latching.** Conversational Tagalog is heavily
  code-switched with English; Whisper will legitimately alternate between `tl` and `en`, and the
  hysteresis described in `README.md:264` will actively suppress correct detections. Japanese with
  English loanwords has a milder version of the same problem. The latching design — correct for most
  cases — is structurally wrong for a listed secondary language.

- **The user's own voice.** Capturing a video call captures both sides. Nothing in the design skips
  translation when the detected language is already English, so English gets "translated" to
  English: wasted latency plus an invitation for the model to paraphrase.

- **Music and podcast intro stings.** Whisper hallucinates aggressively on music. A 15-second intro
  produces confident garbage that flows straight to the translator.

- **BlackHole channel and sample-rate mismatches.** BlackHole 2ch at 48kHz where the source app
  writes only one channel yields half-silent input; Whisper wants 16kHz mono. Resampling is noted in
  the README, but aggregate-device sample rate can change out from under a running session.

- **Stdout buffering.** `print` to a pipe is block-buffered. `bfish listen | tee log.txt` will show
  nothing for a long time — a real gotcha for a tool whose entire value is live output the user is
  likely to pipe. Needs explicit flushing per committed turn.

- **`Foundation.exit()` in an async main.** `Sources/bfish/BFishCommand.swift:19,23` skips cleanup
  and output flushing. Harmless now; it becomes the graceful-shutdown bug later, and
  `README.md:248` requires clean `SIGINT`/`SIGTERM` with audio resources released.

- **Diagnostics as a privacy leak.** `DiagnosticEvent.metadata: [String: String]`
  (`Diagnostics/DiagnosticEvent.swift:18`) is an open door for logging `sourceText`. Combined with
  system-wide capture, redirecting stderr to a file yields a plaintext transcript of everything said
  near the machine — including things said on calls that are not the owner's to retain.
  Recommend an explicit rule now: diagnostics carry segment IDs and timings, never transcript
  content.

- **Hand-rolled argument parsing.** `Sources/bfish/BFishCommand.swift:10` switches on
  `arguments.first`. The no-dependencies decision was right for the scaffold and has an expiry date.
  Adopt swift-argument-parser before `listen` lands, not after.

## 7. Open questions that would change these recommendations

1. **Which Mac, and how much unified memory?** Determines whether concurrent `large-v3` + 7B +
   SpeakerKit is viable at all. This is the difference between "tune the pipeline" and "the live
   design needs a fundamentally smaller model."

2. **Live translation or offline podcast processing — which gets used first?** The plan is currently
   optimized for neither exclusively.

3. **Does the owner read the source languages?** Determines (a) whether the bilingual source+English
   display is signal or noise, (b) whether the 25-point adequacy dimension is scoreable at all, and
   (c) if this is partly a language-learning tool, whether romanization/furigana is needed — the
   domain model has no slot for it, and adding one after `TranscriptTurn` is load-bearing will be
   awkward.

4. **What is the actual source material?** YouTube and podcasts (music stings, single speaker, no
   latency pressure), live calls (two-way, own English in the mix, real latency pressure), or films
   (music, overlap, sound effects). Each stresses a different part of this design.

5. **Is Whisper-direct-to-English acceptable if it wins the bake-off?** If yes, milestone 2 could
   descope most of the remaining plan and the ordering should change immediately. If the LLM is
   wanted specifically for contextual cleanup and tone — a defensible reason — that should be stated
   in the README, because it changes what the scoreboard is actually measuring.
