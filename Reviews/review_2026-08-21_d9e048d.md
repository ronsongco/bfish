## 1. The `languageConfidence` fix is the most valuable find in these commits

`Sources/BFishWhisperKit/WhisperKitRecognizer.swift:113-114,240-243`

```swift
languageConfidence = detection.langProbs[detection.language]
    .flatMap(Self.languageConfidence(fromLogProbability:))
```

WhisperKit's `langProbs` are **log** probabilities. The previous code took them as probabilities
directly, so every `languageConfidence` recorded before this commit was wrong — a true confidence of
0.9967 was being stored as −0.0033.

The consequence nobody has stated: `EnglishBypassPolicy.highConfidenceOnly(minimumConfidence: 0.9)`
compares against exactly this field. With a log probability in it, `(languageConfidence ?? 0) >= 0.9`
was **never true under automatic detection**, so the English-bypass path has been dead code on every
auto-detected file since it was written. It only ever fired with an explicit `--language`, which
hardcodes confidence to 1.

Worth noting how this was caught: it surfaced only because language confidence was pushed into the
JSONL artifact, which was review #8 §6. That is the instrumentation paying for itself, and it is an
argument for continuing to export values rather than only computing them.

## 2. My suggested tolerance fix was wrong, and the evidence shows why

In the preceding discussion I proposed that if the last segment landed near media duration, the
discontinuity was a benign sub-second overlap and a tolerance in the check would do. That was
incorrect, and `docs/whisperkit-long-form-2026-08-21.md:13` identifies the reason precisely: the
boundary carries a **duplicated utterance**, so suppressing the diagnostic would hide real duplicate
output rather than silence a cosmetic warning.

The probe itself was the right instrument — last-segment-end versus media duration is what exposed
the true shape — but the interpretation of that branch was wrong. The conclusion in the doc, that a
tolerance or blind clamp is insufficient and global media time must be preserved while reconciling
overlap at result boundaries, is correct.

The 65-minute data settles the character of the defect:

| | 8:39 | 65:06 |
|---|---|---|
| backward jumps | 1 | 34 |
| jump magnitude | 1.48 s | 0.86–14.45 s |
| last segment end vs media | 514.76 / 518.64 (−3.9 s) | 3930.02 / 3905.92 (**+24.10 s**) |

So it is not chunk-relative reset — offsets are applied — but **accumulating boundary overlap that
eventually pushes the timeline past the media duration**. Jump count scales roughly with duration
(1 per ~9 min, 34 per ~65 min), consistent with one event per chunk boundary.

## 3. Duplicate content is a transcript defect, not only a timestamp defect

This deserves separating from §2 because the fix is scoped differently.

Thirty-four boundaries in the 65-minute file each carry duplicated utterances. Even after timestamps
are reconciled, the duplicated **text** remains unless deduplication is explicit. Downstream that
means, per duplicate: a redundant translation request, redundant latency and token cost, a polluted
`contextTurns` entry consuming character budget, and a visibly repeated line in the user-facing
output.

Since `boundedContext` holds only 4–8 turns, one duplicated turn is a meaningful fraction of the
context window handed to the model.

The reconciliation work in the doc's conclusion should therefore be explicit that it covers both:
restore monotonic global media time **and** drop the duplicated span, ideally with a diagnostic
recording how much was removed so the rate can be tracked across models and fixtures.

## 4. The quality-gating layer is currently a no-op on real audio

This is the finding the probe supports but the doc does not draw, and I think it is the most
consequential one here.

Two measurements, stated separately in the doc:

- "All 142 returned VAD segments reported a zero no-speech probability" (8:39)
- "All returned VAD segments again reported a zero no-speech probability" (65:06, 1,623 segments)
- "1,623 recognized segments and three centrally filtered segments" (65:06)

Together: `maximumNoSpeechProbability = 0.6` **cannot fire** — 1,765 consecutive segments reported
zero. And central filtering caught 3 of 1,623 segments, or 0.18%.

So essentially nothing Whisper emits is being gated on real material. The suppression mechanism
designed across reviews #3–#5 to catch silence hallucinations is inert under
`chunkingStrategy: .vad`, most plausibly because VAD pre-filters non-speech before decoding, so the
decoder never sees a segment it would score as non-speech.

That is not necessarily bad — VAD may be doing the job that `noSpeechProbability` was meant to do —
but it means the project currently has **no evidence-based hallucination control**, and the
threshold it believes is protecting it is unreachable. The music-intro and silence cases that
motivated the gate have not been tested and would not be caught by it.

Three things worth deciding:

1. Whether VAD chunking makes the no-speech gate redundant (in which case say so, and stop treating
   `maximumNoSpeechProbability` as a live safeguard), or whether a non-VAD comparison run is needed
   to see whether the probability becomes informative.
2. What the replacement signal is. `confidence` (`exp(avgLogprob)`) and compression-ratio-style
   repetition detection are the conventional alternatives.
3. **Report the confidence distribution that has already been collected.** The code computes
   `confidenceDistribution` and the two runs emitted it, but the doc records only the no-speech
   result. `minimumConfidence: 0.9` for English bypass is still uncalibrated, and the data to
   calibrate it is presumably sitting in those JSONL files.

## 5. Peak RSS probably understates the memory that matters for concurrency

`peakResidentMemoryBytes` is implemented correctly and the units are right. The question is whether
the number answers the concurrency question.

274.3 MiB peak RSS while a 626 MB model is loaded strongly suggests the model's weights are not
fully counted as resident dirty pages in this process — plausibly memory-mapped and partially
resident, or held by the Neural Engine outside the task's RSS accounting (confidence ~70%).

That matters because the value this number will be used for is `README.md:441`'s contention question:
can `large-v3` and a 7–8 B translation model coexist on this host? Sizing that from a 274 MiB figure
would be badly optimistic.

Suggested refinement: record `phys_footprint` from `task_vm_info` alongside `ru_maxrss` — it is the
metric macOS itself uses for memory pressure and jetsam decisions — and, for the concurrent run
specifically, capture system-level pressure rather than per-process accounting. On a trivial test
binary the two differ (1.66 MiB footprint versus 5.75 MiB max RSS), so they are measuring genuinely
different things and both are cheap to record.

## 6. `TextErrorRate` — two issues that will distort CJK scores

The Levenshtein implementation is correct, with O(n·m) time and O(m) space, and the three-report
structure (raw CER, normalized CER, normalized WER) is a sensible shape.

### 6.1 Word error rate is meaningless for the primary languages

`TextEvaluationNormalizer.words` splits on whitespace and punctuation. Japanese, Mandarin, and
Cantonese have no whitespace word boundaries, so a whole clause collapses into a single "word" and
`normalizedWordErrorRate` will be approximately 1.0 whenever anything differs — while CER shows a 2%
error.

Three of the four primary languages are affected. Reporting both numbers side by side in a
scoreboard invites reading the WER as a quality signal when it carries none. The SDK already
enumerates the non-space-delimited set at `Models.swift:1307` (`zh`, `ja`, `th`, `lo`, `my`, `yue`);
WER should be omitted or explicitly marked not-applicable for those languages.

### 6.2 NFC normalization leaves width differences as errors

`canonicalText` uses `precomposedStringWithCanonicalMapping` — NFC. Japanese ASR evaluation
conventionally uses **NFKC**, which additionally folds full-width to half-width.

Concretely: Whisper may emit `７８９` where a reference has `789`, or `ＡＢＣ` versus `ABC`, and
half-width katakana versus full-width. Under NFC each of those counts as a substitution, inflating
CER for reasons unrelated to recognition quality — and doing so unevenly across models, since
different variants have different output conventions.

`precomposedStringWithCompatibilityMapping` is the one-word change. This matters specifically
because numeric output was made valid content back in review #5, so digits now reach the scorer.

### 6.3 Percentile estimator is nearest-rank

`distribution` uses `Int((count-1) * fraction).rounded()`, i.e. nearest-rank rather than interpolated
percentiles. Defensible for calibration, but it is not the definition most tools use, so scoreboard
values will not be directly comparable to externally computed percentiles. Worth one line in
`docs/diagnostics-schema.md`.

## 7. RTF degrades with duration

0.0770 at 8:39 versus 0.0959 at 65:06 — about 25% worse over 7.5× the length. Still 10.4× real time,
so not a concern in itself.

Worth noting the likely cause is the boundary overlap in §2/§3: reprocessing duplicated spans is
extra decode work. If so, fixing reconciliation should recover some of it, and RTF is a free
secondary check on whether the fix worked.

Memory scaling is the reassuring half of the same comparison: 211.7 → 274.3 MiB for 7.5× the audio
and 11× the segments. Sub-linear, so the batch-accumulation worry from earlier reviews is much
smaller than feared — which weakens the urgency of incremental streaming as a *memory* fix, though
not as a *user-experience* fix.

## 8. Still open

- **Incremental finalized-segment output.** Acknowledged in the doc's conclusion. Now justified by
  user experience rather than memory, given §7.
- **Per-utterance live latency.** Still the number that determines live viability, and still
  unmeasured. Batch RTF on a 9- or 65-minute file does not predict the cost of transcribing a
  4-second utterance in isolation, because fixed per-inference overhead stops amortizing. A handful
  of 3–8 second clips run individually would settle it in minutes.
- **Music and silence behaviour.** Neither fixture appears to have contained a music intro or long
  silence, so the hallucination cases that motivated the gating layer remain untested — see §4.

## 9. Suggested order

1. **Long-form timestamp and duplicate reconciliation** (§2, §3) — preserve global media time, drop
   duplicated spans, record how much was removed. Everything downstream inherits these timestamps.
2. **Report the already-collected confidence distribution** (§4.3) — zero new work, and it is the
   input to the next decision.
3. **Decide the hallucination-gate story** (§4) now that `noSpeechProbability` is known inert.
4. **NFKC and WER gating in `TextErrorRate`** (§6) before any CER numbers are recorded, so early
   scores do not need re-deriving.
5. **Per-utterance latency probe** (§8) — cheap, and it is the live-design decision input.
6. Then incremental streaming, then the translation bake-off.

Items 2 through 5 are all small. Item 1 is the only substantial piece of work, and it is correctly
identified as the next implementation pass in the doc.
