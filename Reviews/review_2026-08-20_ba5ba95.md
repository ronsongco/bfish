## 1. New defect: stderr is no longer a parseable JSONL stream

`Sources/bfish/BFishCommand.swift:58-61`

```swift
statusHandler: { message in
    FileHandle.standardError.write(Data("\(message)\n".utf8))
}
```

Status messages are free text written to the same file descriptor that carries the JSONL
diagnostics, so a run now produces interleaved output like:

```
Resolving WhisperKit model tiny; download may be required
WhisperKit model download: 3%
{"event":"timestamp_repaired","schemaVersion":6,...}
WhisperKit model loaded
{"event":"recognition_completed",...}
```

`README.md:417` states that "stage timing and operational events should be available as JSON Lines
on standard error," and the whole benchmark design depends on machine-readable stderr —
`README.md:510` requires raw results in JSON Lines so runs can be reproduced and re-scored. Any
consumer reading stderr line-by-line as JSON will now fail on the prose lines.

Two independent problems, both worth fixing before the smoke test produces the first artifacts:

1. **Format.** Status should either be JSONL itself (a `model_status` event kind, which fits the
   existing typed-diagnostic design and stays privacy-safe), or go to a separate channel.
2. **Volume.** The progress callback is not throttled or de-duplicated. `Int((fraction * 100)
   .rounded())` emits a line per callback, not per percentage point, so the same percentage repeats
   many times — for the 600 MB+ `large-v3` baseline that is a large volume of duplicate lines
   competing with the diagnostics stream. De-duplicating on changed integer percent is a two-line
   fix.

This is the one item I would place before the first real smoke test, because the smoke test's
output is meant to become evidence.

## 2. `audioDurationSeconds` is summed from SDK per-chunk values

`Sources/BFishWhisperKit/WhisperKitRecognizer.swift:109`

```swift
let audioDuration = results.reduce(0) { $0 + $1.timings.inputAudioSeconds }
```

This sums per-result input duration rather than measuring the file. With `chunkingStrategy: .vad`,
if chunks are padded, overlapped, or if VAD-trimmed silence is excluded, the sum will not equal the
file's true duration.

It is the denominator of `realTimeFactor` — the headline metric for the milestone-2 decision rule —
so an inflated sum understates RTF and a trimmed sum overstates it. Either way the number silently
stops meaning "processing time per second of audio."

I cannot resolve which way it goes without running a model, so this is a *verify* item, not a
defect. It belongs on the smoke-test checklist alongside the timestamp check: compare summed
`inputAudioSeconds` against the file's actual duration read from `AVAudioFile`/`AVURLAsset`. If they
diverge, take duration from the file directly — it is the more trustworthy source regardless.

## 3. Two smaller measurement-semantics issues

### 3.1 `realTimeFactor` includes language detection

`recognitionStart` is taken at line 73, before `detectLanguage`, so `realTimeFactor` covers
detection plus transcription. That is a defensible end-to-end definition, and
`whisper_transcription_wall` is recorded separately so both numbers exist.

The issue is comparability: published WhisperKit and Whisper RTF figures measure transcription only,
so the project's headline number is not directly comparable to external baselines, and the
difference is invisible in the field name. Worth one line in `docs/diagnostics-schema.md` stating
which definition `realTimeFactor` uses — cheaper now than reconciling scoreboard numbers later.

### 3.2 The warm path reports 0 ms rather than omitting the measurement

`WhisperKitRecognizer.swift:135` returns `(whisperKit, 0, 0)` when the engine is already loaded, so
`whisper_model_acquisition` and `whisper_model_load_wall` emit `0` on a warm run.

`README.md:441` requires cold-load and warm-run behaviour measured *separately*. A zero is
indistinguishable from a genuine sub-millisecond measurement or from a missing one, which is exactly
the ambiguity that hurts when aggregating runs later. Omitting those two `StageTiming` entries on
the warm path — or emitting an explicit `modelAlreadyResident` marker — removes it.

Low practical impact today, since each CLI invocation creates a fresh recognizer and is therefore
always cold. It becomes real for any multi-file benchmark run inside one process, which is what the
harness will do.

## 4. `confidence` still repairs silently, inconsistent with the new pattern

`WhisperKitRecognizer.swift:260`

```swift
confidence: min(1, max(0, exp(averageLogProbability)))
```

If `avgLogprob` arrives as NaN, `exp` yields NaN and Swift's `max(0, .nan)` returns `0` (since
`nan >= 0` is false), so `confidence` silently becomes `0` — the value meaning "least confident" —
with no diagnostic.

This is the same class of issue as the `noSpeechProbability` clamp that was just fixed in this
commit, and `ProbabilityRepairField` is already an enum with a single case, clearly shaped to grow.
Adding a `confidence` case and routing this through the same `probability_repaired` path would make
the two probability fields consistent.

Minor, but a segment silently reported as zero-confidence is more misleading than one reported as
repaired, and future quality gates will read this field.

## 5. Note on the accepted abort-on-unknown-token decision

Review #6 §1 had two parts. Adding `yue` is done. The second part — degrade rather than abort on an
unrecognized detected token — was not taken, and
`unknownDetectedLanguageProducesTypedError` now codifies the throw as intended behaviour.

That is a reasonable call, and I am not re-litigating it: a clear error is arguably better than
silently transcribing in a wrong fallback language. Noting only the residual exposure, since it is
cheap to soften:

`WhisperLanguage.supportedTokens` is now pinned to the table of one SDK version. If a future model
or SDK adds a token — `yue` itself was such an addition in large-v3 — a long transcription aborts
with no partial output. Because the adapter now knows this means SDK/model drift rather than user
error, the error message could say so and point at `--language` as the immediate workaround. Same
decision, better failure.

## 6. Test coverage

27 passing, up from 22, with five new tests that map one-to-one onto review #6's gaps:
multi-result mapping with shared timeline and monotonicity reporting, non-file input rejection,
missing-file rejection, the Cantonese table check, and the unknown-token error.

`cantoneseMatchesTheResolvedWhisperKitLanguageTable` is the interesting one — it asserts a property
of the *dependency*, so an SDK bump that changes the language set will surface as a test failure
rather than a runtime abort on real audio. That is the right instinct, and it is the mechanism that
would have caught the original defect.

The gaps corresponding to findings above: nothing covers stderr output shape (§1), and
`audioDurationSeconds`/`realTimeFactor` are computed only on the model-executing path, so neither is
exercised by a test. §1 is testable without a model by capturing the `statusHandler` closure and
asserting every emitted line parses as JSON.

## 7. Sequencing

`README.md` now describes the project as ready for the first real-audio smoke test, and I agree the
adapter is ready. Two items are worth landing first, because both concern the *evidence* the smoke
test produces rather than the code it exercises:

1. §1 — stderr must be parseable, or the run's diagnostics cannot be consumed programmatically.
2. §2 — add the audio-duration cross-check to the smoke-test checklist, so RTF is validated on its
   first use rather than trusted.

Everything else here can follow the smoke test. After it runs, the highest-value review is of the
recorded results themselves — detected language and probability, raw versus repaired timestamps,
RTF, and peak memory — since those are the first real evidence the project has produced and they
determine whether the 2–4 second live target is reachable at all.
