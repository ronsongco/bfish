## 1. The 4.57 seconds can be classified — a reference transcript is not the tool needed

`docs/whisperkit-long-form-2026-08-21.md:79`

> the fixture has no reference transcript capable of proving that all 4.57 seconds represented
> speech

True, but the question does not require a transcript. It requires knowing whether those 24 regions
**contain speech at all**, and the codebase already carries the instrument:
`engine.voiceActivityDetector ?? EnergyVAD()`, at `WhisperKitRecognizer.swift:253`.

Run the VAD over the 24 uncovered ranges — 4.57 seconds of audio in total:

- **Non-speech** → the discarded decoder output was emitted into silence, dropping it was correct,
  and the finding closes with no residual risk.
- **Voiced** → real speech was captured only by an out-of-window emission and lost when it was
  removed, which is a genuine content-loss bug and would justify recovering rather than discarding
  those ranges.

The prior strongly favours the first, and it comes from the project's own evidence. The
hallucination probe established that Whisper emits confident text on digital silence — confidence
0.94, no-speech probability 0, normal compression ratio. An out-of-window emission into a region the
next window's VAD declined to stage is precisely that phenomenon: the decoder running past its input
into nothing and inventing plausible text.

That also explains the 24-versus-17 split. The 17 covered ranges are regions where the following
window did find speech and transcribed it properly; the 24 uncovered ones are where it found none.
If the VAD confirms that, two separate findings resolve into one coherent account, and the
reconciliation can be described as removing hallucinated overshoot rather than as lossy.

This is a few minutes of work against audio already on hand, and it converts the last open
qualitative question in the recognition workstream into a measured one.

## 2. Normalization writes at the source rate and channel count

`Sources/BFishWhisperKit/WhisperKitRecognizer.swift:558-571`

```swift
AVSampleRateKey: format.sampleRate,
AVNumberOfChannelsKey: Int(format.channelCount),
AVLinearPCMBitDepthKey: 16,
```

The temporary file inherits the source's sample rate and channel count. Whisper consumes 16 kHz
mono, so for a typical 44.1 kHz stereo podcast the file is written at 176,400 bytes/s — about
**689 MB for this 65-minute fixture**, where 16 kHz mono would be roughly 125 MB.

Writing 16 kHz mono instead would gain three things at once:

1. **~5.5× less temporary disk**, which matters directly for §3 below.
2. **No repeated downmix and resample per window.** Every staging read currently passes
   `channelMode: .sumChannels(nil)` and lets WhisperKit resample, so the same conversion is
   performed on every window rather than once during normalization.
3. **Reproducibility with the manual path.** The doc already identifies that preserving native
   representation changes VAD boundaries relative to the `ffmpeg`-downmixed fixture. Normalizing to
   16 kHz mono makes the automatic path produce the same input the manual path did, which removes a
   confound from every future comparison.

One accuracy note: this is not a two-key change. `AVAudioFile` converts bit depth and interleaving
on write but does not resample, so it needs an `AVAudioConverter` between read and write, or an
`AVAssetReader` configured with 16 kHz mono output settings. A modest amount of code, but not free.

## 3. The temporary file has no space check and no interrupt-safe cleanup

Two gaps around the same artifact, both worth closing while the code is fresh.

**No disk-space precheck.** At native representation, a 3-hour 48 kHz stereo podcast produces roughly
a 1.4 GB temporary file in `FileManager.default.temporaryDirectory` on the system volume. Nothing
checks available space before the write begins; exhaustion surfaces as a generic
`audioNormalizationFailed` partway through, after the user has already waited. `bfish doctor` checks
for ≥20 GiB, but that is a different moment and does not account for the input being processed.
Estimating required bytes from duration and format and checking once before writing is cheap. §2
also reduces the requirement by 5.5×, which is the better half of the fix.

**`defer` does not survive a signal.** `transcribe` relies on
`defer { preparedAudio.removeTemporaryFile() }` at line 114, which runs on normal return and on
thrown errors but not on `SIGINT`. Interrupting a long transcription — a realistic action given
these run for minutes — orphans a multi-hundred-megabyte file.

Clean `SIGINT`/`SIGTERM` handling has been an open README requirement (`README.md:248`) since the
first review, deferred reasonably while nothing held resources. This is the first concrete resource
that leaks without it, which moves it from a live-capture prerequisite to something with a present
cost.

## 4. Normalization is strictly sequential ahead of recognition, and need not be

First-segment latency went from 1,973 ms to **7,030 ms** on the same fixture, with 4,410 ms of that
being normalization that completes entirely before recognition begins.

Both operations are sequential streaming passes over the file. Decoding produces PCM front-to-back;
staging consumes it front-to-back. They can overlap: once the first ~30 seconds are decoded, window
one can be staged and recognized while decoding continues behind it. That would restore
first-segment latency to roughly the PCM figure for compressed inputs.

The scaling argument makes it worth doing rather than accepting: normalization time is linear in
duration, so a 3-hour recording waits about 12 seconds before any output appears, and a longer one
proportionally more. For a tool whose streaming output was a deliberate design goal, paying a
duration-proportional delay before the first line is a regression specific to the format users are
most likely to supply.

Not urgent — 7 seconds on a 65-minute file is tolerable — but it is the kind of thing that is much
easier to build now, while the staging loop is the only consumer, than after live capture shares it.

## 5. Smaller notes

**Double open in `prepareSeekableAudio`.** Line 541 opens the file as `probe` for the format check,
then line 552 opens it again inside the `do` block. The probe is discarded. Harmless, trivially
avoidable.

**RTF accounting is honest.** 0.09738 including normalization versus 0.09583 without, with the
difference attributed explicitly. Reporting the inclusive number as the headline is the right choice
for a user-facing metric.

**Memory held steady.** 203.9 MiB RSS and 93.0 MiB physical footprint on the direct-MP3 run, against
190.8 / 90.8 on the PCM run — normalization did not introduce retention. The earlier caveat still
applies: neither metric captures model weights, so concurrency planning for the bake-off needs
system-level measurement.

**Music and speech-over-music remain the untested case.** Unchanged and still correctly flagged. It
is now the only substantive gap in the recognition workstream's evidence.
