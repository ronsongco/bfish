## 1. The Whisper translate result is now real, but the conclusion may be broader than the evidence

The test is sound and the result stands for what was tested: `large-v3-v20240930_626MB` under
WhisperKit 1.1, given the translate decoding task, returns source-language text for all four
fixtures.

What is not established is **why**, and the three candidate causes have very different implications:

1. **A `large-v3` regression.** Whisper large-v3's translate task is reported to behave worse than
   large-v2's, including cases of the model ignoring the translate token and transcribing instead.
   Confidence this is the cause: ~65%. If so, `large-v2` or `small` would translate normally.
2. **The compressed Core ML conversion.** The `626MB` variant is a quantized repack. The translate
   path depends on a different special-token sequence, and a conversion or tokenizer gap could break
   it while leaving transcription intact.
3. **WhisperKit's task wiring.** Least likely, given the CLI printed the selected task explicitly —
   though printing the intent does not prove the token reached the decoder.

The table says "Ineligible for this tested configuration," which is correctly scoped. But the
Decision section reads more absolutely, and the next implementation gate no longer mentions Whisper
direct at all — it has effectively left the roadmap. That is the risk worth naming: a defect
specific to one quantized variant closing a strategic option permanently.

The distinguishing test is cheap. Run the same four fixtures through the same CLI with one other
variant — `small` is a fast download and would settle causes 1 and 2 together. Perhaps twenty
minutes including the fetch.

Why it is worth twenty minutes: if any variant translates correctly, the conclusion changes from
"Whisper direct is ineligible" to "this variant is broken for translate; use X," and the
zero-additional-memory, zero-additional-load, zero-additional-latency argument returns intact. That
option remains the only one that could remove the Ollama workstream entirely, and `README.md:262`
still describes Whisper direct as "an early comparison baseline, not merely a deferred fallback."

## 2. The omitted-subject fixture sets up the test but does not score it

`Benchmarks/Fixtures/translation-adapter-v2.jsonl`, `context-ja-001`:

```json
"recentContext": [{"sourceText":"田中さんはまだ会社にいます。","englishText":"Tanaka is still at the office."}],
"sourceText": "もうすぐ着くと言っていました。",
"referenceEnglish": "They said they would arrive soon.",
"requiredTerms": ["said", "arrive soon"]
```

The property under test is whether the model uses context to resolve the dropped subject — that is
the entire reason this fixture exists, and the capability I flagged as most distinguishing for
Japanese and Korean.

But the subject appears in neither `requiredTerms` nor, unambiguously, in the reference. A model that
ignores context entirely and outputs *"I said I would arrive soon"* — the natural first-person
reading of a subjectless Japanese sentence — contains both `"said"` and `"arrive soon"` and
therefore **passes**. The one thing the fixture is for is the one thing it does not check.

Two options, either sufficient:

- Add the expected subject to `requiredTerms` (`"Tanaka"`, or accept a third-person pronoun), and
  choose a reference that commits to it rather than using singular *they*.
- Add a `forbiddenTerms` field and populate it with first-person forms, which also generalizes to
  the other three context fixtures and to future ones.

The same check should be applied to `context-ko-001`, `context-zh-001`, and `context-pt-BR-001`,
which share the structure. Worth fixing before the fixture is used to compare 4B against 12B, since
context handling is exactly where a size difference would be expected to show.

## 3. Smaller notes

**The prompt's empty-input rule is unreachable from the fixture set.** Both safety fixtures carry
`expectedDisposition: "suppress-before-translation"`, meaning the pipeline filters them before the
model is called — which is the correct behaviour and matches `README.md:393`. The consequence is that
the prompt's rule "If CURRENT_SOURCE_TEXT is empty or contains only non-speech notation, return
`{"english_text":""}`" is never exercised by these fixtures. It is sensible defence in depth, but it
is currently untested; a fixture that deliberately bypasses the filter would close that.

**`requiredTerms: ["Friday", "2", "not tomorrow"]`** on the degraded fixtures is a good shape for
checking negation survival. `"2"` is a weak token — it matches any occurrence of the digit — but the
combination with `"not tomorrow"` carries the actual signal, so this is minor.

**Ten fixtures across four languages and four test types** is right-sized for adapter development
and correctly not presented as a benchmark. FLEURS and FLORES remain the gate for scored evaluation,
as `README.md:433` states.
