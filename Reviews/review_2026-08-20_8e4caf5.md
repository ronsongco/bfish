## 1. New defect introduced by the §1.4/§1.5 correction

### 1.1 Numeric-only segments are now silently discarded — verified

`Sources/BFishCore/Pipeline/TranslationPipeline.swift:240-249`

The filter's final clause returns `.noLetters` when a segment contains no character in
`CharacterSet.letters`. Digits are Unicode category `Nd`, not `L*`, so any utterance transcribed as
bare numerals is filtered out: no transcript event, no translation, only a diagnostic.

Reproduced against the exact predicate from the source:

| input | result |
|---|---|
| `2026` | **noLetters — dropped** |
| `42` | **noLetters — dropped** |
| `3.14` | **noLetters — dropped** |
| `50%` | **noLetters — dropped** |
| `$100` | **noLetters — dropped** |
| `７８９` (full-width) | **noLetters — dropped** |
| `1999年` | PASS (年 is `Lo`) |
| `。。。` | noLetters — dropped (correct) |
| `（笑）` | annotation — dropped (correct) |

Whisper routinely emits digit-only segments for short numeric utterances — a year, a price, a score,
a room number, a percentage in isolation. Each of those now vanishes from the transcript.

This is directly adversarial to a scored requirement: the scoreboard allocates 10 points to
"Details and entities — names, numbers, dates, units" (`README.md:456`), and
`README.md:424` lists "names, places, dates, money, percentages, measurements" as required corpus
content. The pipeline currently drops precisely that class of segment before the translator sees it.

Recommendation: the intent of the clause is "contains no linguistic content." Digits, currency
symbols, and percent signs are content. Widen the predicate to letters **or** digits — i.e. filter
only when a segment has neither — or gate on `CharacterSet.alphanumerics`. The `。。。` and `♪` cases
still filter correctly under that change.

Worth a test row alongside the existing bracket table; the parameterized test added for §1.5 is the
natural place.

## 2. Re-raised from review #3 — not addressed

### 2.1 Head-of-line blocking and missing lag instrumentation (review #3 §1.6)

Unchanged in this commit. `TranslationPipeline.swift:83-88` still processes segments strictly
serially, awaiting each translation before touching the next, and `PipelineProfile.live` still sets
`translationTimeout` to 15 seconds against a stated 2–4 second target (`README.md:101`).

Restating the two consequences, since neither is visible from the code alone:

- **Spike:** one stalled translation produces fifteen seconds of no output while live audio keeps
  arriving.
- **Steady state:** if translation averages 3s and utterances arrive every 2s, the pipeline falls
  behind by 1s per utterance indefinitely. There is no pending-translation bound, no queue-depth
  diagnostic, and no recovery policy — all three required by `README.md:223-225`.

`AudioBufferingPolicy` bounds the audio side; nothing bounds the translation side, which is where
the backlog actually forms.

This has a direct dependency the plan should account for: the opt-in memory-oversubscription run
described at `README.md:513` is meant to observe whether degradation is *visible*. With no lag
instrumentation, that experiment would currently measure a pipeline incapable of reporting the
thing being tested. Queue-depth and lag diagnostics are a prerequisite for it, not a follow-up.

Suggested minimum before live capture: shorten the live timeout into the latency budget (~5s), add a
pending-translation depth bound with a diagnostic when exceeded, and decide the recovery policy
(drop oldest pending, or emit source-only and move on).

### 2.2 Session lock has no diagnostic or recovery path (review #3 §2.3)

Unchanged. `activeSessionID` is set inside `events(...)` before any consumer iterates, so a caller
that creates a stream and retains it without consuming holds the instance locked.
`sessionAlreadyRunning` carries no session identifier, start time, or hint, and no diagnostic event
is emitted for the rejected attempt. Self-heals on stream deallocation.

Low severity while the only callers are tests and `process(...)`; worth closing before a UI target
can hold streams.

## 3. Smaller new observations

### 3.1 `SessionLocale` is session-scoped in name but per-segment and unvalidated in fact

`Sources/BFishCore/Domain/LanguageTag.swift:1-24`, `TranscriptModels.swift:107,147`

The type carries no validation or normalization — `SessionLocale("PT-br")` and
`SessionLocale("nonsense")` are both accepted, and the value now flows into terminal output and into
`TranscriptTurn`'s `Codable` representation.

More structurally: it is optional and set per `RecognizedSegment`, with nothing enforcing that
segments in one session agree. That is inconsistent with `CaptureTimeline`, which this same commit
promoted to a required session-scoped field. Both are session concepts; only one is modeled that
way.

Display-only, so severity is low — but if it is genuinely a *session* locale, the pipeline session
is its natural home, and the adapter should not have to remember to stamp every segment.

### 3.2 Diagnostic schema is at version 3 with no changelog

`DiagnosticEvent.currentSchemaVersion` has gone 1 → 2 → 3 across three commits, which is the right
discipline. But `Benchmarks/Runs/` is gitignored and nothing records what each version means.

Re-scoring historical runs is an explicit goal (`README.md:510`). That requires a durable mapping
from schema version to field set. A short `docs/diagnostics-schema.md` appended to on each bump
would cost almost nothing now and is unreconstructible later.

### 3.3 The post-`await` session guard drops a completed translation silently

`TranslationPipeline.swift:156,171` — the new guards correctly prevent stale appends, but on the
cancellation path a translation that has already succeeded is discarded with no transcript and no
diagnostic. Acceptable, since the stream is terminating anyway and the consumer would not observe
it. Noting only that "work completed then thrown away" is the one case in the pipeline that now
produces no record at all.
